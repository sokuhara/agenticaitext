Coding Agentの中心にはLLMがあります。ただしLLMは、それ単体ではファイル1つ読めません。この章では、LLMが何をする部品で、どこで、なぜ間違えるのかを押さえます。

1.1LLMは何をする部品か

大規模言語モデル（LLM）は、巨大なニューラルネットワークです。膨大なテキストで学習されています。

やっていることは単純です。これまでの文脈から、次に来る言葉を1つ選ぶ。それを繰り返します。

次のトークンを予測して繋げる。この繰り返しだけで文章とコードが出てきます

この最小単位をトークンと呼びます。英語では単語より細かく分割されます。日本語では文字や語句にまたがります。「hello」は1トークンです。「こんにちは」は2〜3トークンです。

LLMは、入力をトークンに変換してから処理します。

この繰り返しから、翻訳、要約、対話、プログラミングが生まれます。とくにコードは得意です。理由は2つあります。形式が厳密であること。学習データが大量にあることです。

1.1.1部品としての限界

ここが出発点です。LLMは、テキストを受け取ってテキストを返す部品です。それ以上のことはしません。

できないこと
ファイルを読む
コマンドを実行する
いま何が起きているかを知る（知識は学習時点で止まっています）
自分の答えが正しいか確かめる

どれほど賢くても、LLM単体ではコードベースに触れません。

この4つをどう埋めるか。それがCoding Agentの設計です。1.2で限界を見ます。PART 3で埋め方を見ます。

推論過程が見えるモデルについて 答える前に、思考の途中経過を出力するモデルがあります。ollama run qwen3.5:4b を実行すると、本文の前に <think> の中身が長く流れます。処理は止まっていません。待ってください。

ただし、そこに出るものを「モデルの本当の思考」と考えないでください。あれも生成されたテキストです。最終的な答えと矛盾することもあります。参考にはなります。根拠にはなりません。

1.2コンテキストと誤り

LLMで詰まる場面は、2種類しかありません。入りきらないか、間違っているのに自信があるかです。

1.2.1コンテキストウィンドウ

LLMにはコンテキストウィンドウという制限があります。ワーキングメモリにあたります。入力と出力の合計トークン数が、この範囲に収まる必要があります。

2026年の上位モデルには、100万トークン級のものもあります。手元で動かすモデルでも、20万トークン以上に対応するものがあります。

ただし「対応している」と「実際に使える」は別です。

2つの落とし穴 1. 設定しなければ使えない。
ローカルで動かす場合、ランタイム側の既定値のほうが小さいことがあります。モデルが26万トークンに対応していても、num_ctx を設定しなければ既定値で切られます。エラーは出ません。履歴が静かに消えます。（付録A A.3.2）

2. 長いほど賢いわけではない。
コンテキストの真ん中にある情報は、取りこぼされることがあります。Lost in the Middle と呼ばれます。長さを伸ばしても解決しません。

Coding Agentが長い作業の途中で、さっき作ったファイルを忘れることがあります。原因はたいていここです。

対処は2つあります。途中で履歴を要約すること。新しいセッションへ引き継ぐこと。PART 6で実際に行います。

1.2.2知識は学習時点で止まっている

モデルが知っているのは、学習が終わった時点までの世界です。

ライブラリのAPIは変わります。非推奨になった書き方も、モデルの中には残っています。新しいバージョンは知りません。

「動くけれど古い書き方」が出てくる原因の多くは、これです。

1.2.3もっともらしい誤り

ハルシネーションとは、事実と異なる情報を、本当のように答える現象です。

「2025年8月に発表された新しいプログラミング言語について教えて」
→「NeoScript は、JavaScriptの非同期処理を根本から見直し、GoogleとMetaが共同で開発しました…」
（そのような言語も、発表も存在しない）

厄介なのは口調です。正しい答えと誤った答えが、まったく同じ口調で返ってきます。自信のなさは表示されません。

だから「AIが嘘をつく」と身構えても、あまり役に立ちません。必要な情報を与えないまま答えさせると、それらしいもので埋まる。そう理解するほうが実用的です。

演習0の回収 演習0で、3か国について仕事を挙げてもらいました。そのうち1つは、ほとんど知らない国だったはずです。それでも表は埋まりました。

いま説明したことが、数十分前にあなた自身の手で起きています。

あのとき ※推測 と ［前提：……］ を書いてもらったのは、このためです。根拠のある記述と、埋めただけの記述を、後から区別できるようにしておく。これがそのままAgentを扱う技術になります。

対処はグラウンディングです。外部の正確な情報源を与え、その根拠に基づいて答えさせます。

手段は2つあります。RAGとTool Useです。Tool Useが、PART 3で扱う内容になります。PART 6で llms.txt をローカルに置いてから実装させるのも、同じ考えです。

1.3演習：モデルの限界を自分で確かめる

1.1と1.2で説明したことを、手元のモデルで再現します。読んで納得するのと、自分の画面で起こすのとでは、後の理解が変わります。所要20分。

ターミナルの開き方とモデルの入れ方はセットアップにあります。まだの人は先に済ませてください。

ollama run qwen3.5:4b

1.3.1実験1：知識は学習時点で止まっている

PROMPTあなたの知識は、いつの時点までのものですか。 そのあとに起きた出来事を1つ挙げて、内容を説明してください。

後半を求められると、多くのモデルはそれらしい出来事を作ります。「知りません」と答えるモデルもあります。どちらが返ってきたかを記録してください。

1.3.2実験2：もっともらしい誤り

PROMPTPython の標準ライブラリにある quickload モジュールの使い方を、 コード例つきで説明してください。

そんなモジュールはありません。それでも、動きそうなコード例が返ることがあります。返ってきた文章の口調を見てください。正しい答えのときと、区別がつくでしょうか。

ここが要点です 誤りは、誤りらしい顔をして出てきません。自信のなさは表示されません。だからPART 4以降で、機械が判定する仕組みを外側に置くことになります。

1.3.3実験3：冒頭の指示は最後まで守られるか

配布する長文ファイルを使います。冒頭にだけ決まりが書かれていて、末尾で質問が来るという構成です。

同じ内容で、長さの違うものが5つあります（experiment3/）。短いものから順に投げて、どこで決まりが守られなくなるかを見ます。

ファイル文字数目安トークン
exp3_short.md約1,200約600
exp3_medium.md約2,100約1,000
exp3_long.md約3,400約1,700
exp3_xlong.md約6,900約5,700
exp3_xxlong.md約12,100約10,100

冒頭に書かれている決まりは3つです。

1. 回答は箇条書き3点にすること。それ以上でも以下でもいけない。
2. 各項目は40字以内に収めること。
3. 前置きと後書きを書かないこと。箇条書きだけを出力すること。

末尾の質問は「ピーク帯の注文の扱いを説明せよ」です。答えは文書の中央付近にあります。

やり方

  1. ターミナルで ollama run qwen3.5:4b を起動する
  2. VS Codeで experiment3/exp3_short.md を開く
  3. Ctrl + A で全選択し、Ctrl + C でコピーする
  4. ターミナルに貼り付けて、そのまま Enter を押す
  5. 出力が決まりを守っているか記録する
  6. medium、long、xlong、xxlong と順に上げて、同じことを繰り返す
質問文を自分で足さないこと ファイルの末尾に、質問はすでに書かれています。貼り付けたら、何も付け足さずにEnterを押してください。

「この文書について答えて」などを自分で書き足すと、それが末尾に来ます。冒頭の決まりからの距離が変わってしまい、実験になりません。
貼り付けがうまくいかないとき ターミナルによっては、長い文章を貼ると途中で改行が実行されてしまいます。その場合は、貼り付けの前に Shift を押しながら貼るか、ollama run ではなくファイルを渡す形にしてください。

Get-Content exp3_short.md | ollama run qwen3.5:4b（PowerShell）
cat exp3_short.md | ollama run qwen3.5:4b（macOS / Linux）

この方法のほうが確実です。1行で済み、貼り付け事故も起きません。

決まりが守られるかを見てください。崩れ方には段階があります。「守られた／守られなかった」の2択ではなく、どう崩れたかを記録します。

段階症状
13点だが、1項目が40字を超える
2前置きが付く（「はい、説明します」など）
3項目数が4つ以上、または2つになる
4箇条書きですらなくなる
5質問と関係のない内容を答える
6中央にある第7章ではなく、文書の冒頭や末尾の内容を答える

6番が出たら、それがLost in the Middleです。コンテキストの真ん中が落ちています。

短い実験で済ませたい場合 num_ctx を小さく設定した実験用モデルを使うと、同じことが数往復で起こります。設定は付録AのA.3.2です。

逆に言えば、この現象は「モデルが忘れっぽい」のではなく「入る量に限りがある」だけです。設定次第で起きたり起きなかったりします。

これが、Coding Agentが長い作業の途中で「最初に決めたルール」を守らなくなる現象と同じものです。

実験記録すること

1.4ここまでで分かったこと

LLMは、コードも文章も生成できます。学習した膨大なコードから、それらしく動くものを組み立てられます。

しかし、生成したコードが動くかどうかを、自分では確かめられません。ファイルを開けず、テストを走らせられず、エラーメッセージを読めないからです。1.1.1で挙げた4つの制約が、そのまま残っています。

次のPARTでは、まずAIと対話しながらコードを作ります。速さを体験すると同時に、LLMだけに任せたとき何が足りないかを見ます。
