8.0この章で何をするか

この章で学ぶこと

PART 7で作ったAgentには、状態、ツール、分岐、承認がありました。その設計を、コーディング以外の仕事へ移します。

動画制作は題材です。目的は2つあります。複数段階の仕事を分解すること。機械が判定する部分と、人間が判断する部分を分けること。

この章を終えると

企画から公開判断までを持つ制作ワークフローを設計できるようになります。修正ループを含むNotebookを作れるようになります。

この章で繰り返す進め方

1　仕事を分解する

2　状態とツールを決める

3　人間の承認位置を決める

4　実行する

5　失敗したら戻す

PART 7の plan → implement → check → 分岐 と同じ形です。工程の数が増えるだけで、考え方は変わりません。

8.0.1最終課題

FINAL MISSION「学生が知るべき地域の魅力」「大学生活で本当に役立つこと」「身近な社会課題」からテーマを1つ選び、1分の解説動画を完成させる制作Agentを作りなさい。 Agentは、構成を考え、根拠を確認し、台本を作り、素材の指示を出し、 動画を組み立て、チェック結果を見て修正する。 人間は、企画の承認、事実確認、公開判断を行う。
これは動画コンテストではありません 評価するのは映像の見栄えではありません。仕事をどう分解したか、どこに人間の確認を置いたか、失敗したときにどう戻したかです。凝った映像でも、評価は低くなることがあります。Agentの流れが1本道で、承認も再試行もない場合です。

逆に、素材が文字と静止画だけでも構いません。根拠確認のノードがあり、しきい値で人間に渡す設計なら、良い提出物です。

8.0.3VS CodeからColabにつなぐ

Colabはブラウザでも使えますが、VS Codeから接続できます。PART 3以降と同じ環境のまま、GPUだけを借りる形です。

ブラウザのColabVS Codeから接続
編集ColabのエディタVS Code。Clineも使える
Gitやりにくいそのまま使える
Driveのマウント必要不要
ファイルの受け渡しブラウザ経由右クリックで送受信

接続の手順

  1. 拡張機能のパネル（Ctrl + Shift + X）で Colab を検索し、発行元が Google のものを入れる
  2. 作業フォルダに .ipynb ファイルを作る
  3. 右上の Select Kernel を押す
  4. Colab を選ぶ
  5. New Colab Server (CPU, GPU or TPU) を選ぶ
  6. Googleアカウントへのアクセスを聞かれたら Allow
  7. ブラウザが開いたら、画面の指示に従う
  8. VS Codeに戻り、GPU を選ぶ
  9. アクセラレータの一覧から T4 GPU を選ぶ

つながったか確認する

セルに次を貼って実行します。

8.1動画制作を「仕事の流れ」に分ける

まず、動画を作る仕事を工程に割ります。演習0でやったことと同じです。

繰り返しで、多段階で、いまは人がやっている仕事。それを分解します。

企画　テーマから、伝えたい要点を3つに絞る

根拠確認　その要点が事実か確かめる。出典を残す

台本　1分（およそ300字）に収まる原稿を書く

絵コンテ　各カットに何を映すかを指示する

素材　画像、音声、字幕を用意する

組み立て　ffmpegで1本の動画にする

評価　尺、字幕のズレ、音量、誤りを点検する

PART 7の plan → implement → check と同じ形です。違うのは工程の数と、checkが機械的に判定しきれないことです。テストは通るか通らないかですが、「この動画はよいか」には自動判定がありません。

8.1.1だから確認を2種類に分けます

機械が判定できること人間が判定すること
尺が55〜65秒に収まっているか企画が趣旨に合っているか
字幕の総文字数が台本と一致するか事実として正しいか
音声と字幕のタイムコードがずれていないか誤解を招く表現がないか
出力ファイルが再生できるか公開してよいか

左の列はcheckノードにします。右の列はinterruptにします。この振り分けが、この課題の設計そのものです。

from typing import TypedDict


class VideoState(TypedDict, total=False):
    theme: str
    points: list[str]        # 要点3つ
    sources: list[str]       # 根拠の出典
    script: str              # 台本
    shots: list[dict]        # 絵コンテ
    caption_only: bool       # 音声なし・字幕のみで作るか
    audio_path: str
    subtitle_path: str
    video_path: str
    check_report: dict
    attempts: int
    approved: bool

PART 7の State と構造は同じです。工程が増えただけで、考え方は変わりません。

スターターNotebookを使ってください ffprobeの呼び出し、字幕の生成、ffmpegの組み立て、グラフの雛形。これらはスターターNotebook（part8_starter.ipynb）に入っています。ゼロから書くと、動画処理のデバッグに時間を取られて、この章の主題に届きません。

あなたが設計して書き換えるのは、次の4つだけです。
1. 状態（VideoState に何を持たせるか）
2. 承認の位置（どこで interrupt するか）
3. 戻り先（落ちたとき、どの工程へ戻すか）
4. 検査条件（機械が判定するのは何か）

8.3企画から絵コンテまでをAgentに任せる

ここは文章を作る工程です。企画、根拠確認、台本、絵コンテを順に通します。まずは「見た人が、誰に、何をしてほしい動画か」を1文で決めてください。これが曖昧だと、Agentはもっともらしい映像を足すだけになります。

根拠確認のノードを飛ばさないこと LLMに台本を書かせると、それらしい数字と固有名詞が混ざります。自然に混ざるので、読んでも気づきません。PART 1の1.2.3で見たとおりです。演習0で ※推測 を付けてもらったのは、まさにこの練習でした。

要点ごとに出典を sources に残し、出典のない要点は台本に進ませない。これをノードとして実装してください。「気をつける」では実装になりません。

標準課題では、出典は学生が3本入力します。ワークフローがWeb検索で事実を作ることはしません。発展課題では、検索やMCP、外部APIで候補を集めても構いません。ただし、最後の事実確認は人間が行います。

絵コンテまで出来たところで、1回目の人間の承認を入れます。

def review_plan(state: VideoState) -> VideoState:
    decision = interrupt({
        "points": state["points"],
        "sources": state["sources"],
        "script": state["script"],
        "question": "企画と事実確認は妥当ですか？ (approve / revise)",
    })
    return {**state, "approved": decision == "approve"}

ここで止める理由は、この先が取り消しにくいからです。音声合成と動画のエンコードは時間もコストもかかります。台本が間違ったまま先へ進むと、作り直しの範囲が一気に広がります。7.4の「取り消せない操作の前」に該当します。

8.4承認後、動画に組み立てる

承認が出てから、素材を作り、1本にまとめます。

ffmpeg -y \
  -f concat -safe 0 -i shots.txt \
  -i narration.wav \
  -vf "subtitles=subtitles.srt" \
  -c:v libx264 -pix_fmt yuv420p -c:a aac -shortest \
  output.mp4

この工程はAgentに書かせて構いませんが、コマンドは必ず自分で読んでください。ffmpegのオプションは、間違っていても静かに違う結果を出します。エラーで止まってくれるとは限りません。

失敗が多い箇所 画像の解像度がカットごとに違う。音声のサンプリングレートが揃っていない。字幕のエンコーディングがUTF-8でない。フレームレートの指定漏れで尺が変わる。どれもffmpegは動いてしまいます。だから8.5の inspect_video が要ります。

8.5評価し、修正ループを回す

出来た動画を検査します。8.1.1の左の列を、そのままコードにします。

def check_video(state: VideoState) -> VideoState:
    info = ffprobe(state["video_path"])
    report = {
        "duration_ok": 55 <= info["duration"] <= 65,
        "has_audio": info["has_audio"],
        "subtitle_chars": count_chars(state["subtitle_path"]),
        "script_chars": len(state["script"]),
    }
    report["passed"] = (
        report["duration_ok"]
        and (info["has_audio"] or state["caption_only"])
    )
    return {**state, "check_report": report}

caption_only は、音声なしで仕上げるルートを通すための項目です。字幕だけで完成させられます。標準課題でTTSが使えなくても、検査で落ちません。

落ちたら、どの工程へ戻すかを決めます。全部やり直すのではありません。尺が長ければ台本へ、音がなければ素材へ、字幕がずれていれば組み立てへ戻します。

def route(state: VideoState) -> str:
    r = state["check_report"]
    if r["passed"]:
        return "review_final"
    if state["attempts"] >= 3:
        return "give_up"
    if not r["duration_ok"]:
        return "script"          # 台本まで戻る
    return "assemble"            # 組み立てだけやり直す

提出要件：修正ループを最低1回は回してください。

最初の1回は必ず落ちます スターターNotebookは、初期設定で動画が約70秒になるようにしてあります。55〜65秒の条件を満たさないので、1回目の検査は必ず失敗します。仕込みです。

落ちてから、どこへ戻すかを設計してください。台本へ戻して要点を短くするのか、絵コンテへ戻して1カットの秒数を詰めるのか。この課題で見たいのは、失敗したときに何が起きるかです。

8.6公開できない理由を確認する

動画が完成しても、それは「公開してよい」を意味しません。最後の承認の前に、次を確認します。

観点確認すること
誤情報要点3つに出典があるか。出典が本当にその内容を述べているか
著作権画像、音楽、フォントの利用条件。生成物の学習元が問題にならないか
肖像実在の人物が映っていないか。似せていないか
生成物の表示AIが作ったことを示す必要がある場面か
コスト1本あたりいくらかかったか。何回作り直したか
ログどの工程で何を実行したか、後から追えるか
