6.1What you add in this part

MISSIONAdd one feature to the Flask Vibe Chat from Part 5. What it is arrives partway through this part. Do not break a single existing test.

6.1.1What difference the tests make

In Part 4, after the fix you checked Send and Delete by hand, because the agent's report was not evidence.

Now you have tests. After adding a feature, one pytest tells you whether the old behaviour still holds.

This is what "tests as a shield" means Tests do not prove your code is correct. They tell you that behaviour you already checked once is still there.

Checking everything by hand after every change is not sustainable. So you write the checkable parts down while you still remember them. That is what Part 5 was for.

6.1.2The starting files

As in Part 5, everyone starts from the same folder. It is the app as it stands at the end of Part 5: the Flask version, with Delete and the 200-character limit on the server side, and two tests. Use this one, not your own folder.

Download vibe-chat-part6-starter.zip

Unzip it to get a vibe-chat folder. Open that folder in VS Code and, in the terminal:

pip install flask pytest
pytest

2 passed means you are ready. Your own folder from Part 5 is untouched if you keep it somewhere else. If you use a virtual environment, create it inside vibe-chat as in Part 5.

6.1.3Before you start

Before adding anything, make sure pytest passes right now. If you saw 2 passed above, that is done.

Add features on top of a failing test suite and you will not be able to tell whether a later failure is old or new.

6.2Five steps for every change

You add the feature in these five steps. Learn them first. 6.3 walks through them in order.

1　Write the finish conditions　what has to be true to be done

2　Predict what will change　which file, and where in it

3　Ask in Plan mode　read the plan before it builds

4　Approve the diff　compare it with your prediction

5　Check with pytest and the browser　both of them

6.2.1What happens if you skip one

SkippedWhat follows
1 conditionsThe agent works to its own idea of finished, and you have nothing to compare against
2 predictionYou read the diff without being able to judge it
3 planYou notice the wrong approach after it has been built
4 approvalUnrelated code gets rewritten
5 checkingTests pass while the page is broken
Step 2 is the one people skip Read a diff without a prediction and you will think you are reading it when you are not. It becomes "looks like reasonable code, Save".

Write down "this function in app.py and this part of templates/index.html should change" beforehand. Then a diff that touches something else stands out immediately.

6.3An unplanned change request

Requirements change after something already works. In real work, this is the normal case.

Urgent Suppose a report comes in: someone posted a message containing language aimed at hurting another person.

Make it impossible to post a message containing a banned word. Keep the list of banned words in app.py.

When a post is refused, show the reason on the page. Do not break anything that already works.

6.3.1Predict first

Write this before you ask. Predicting and then reading a diff is a completely different activity from reading one cold.

  • How does the data change? Where does the banned-word list live?
  • How does the logic change? At what point in sending is the check made?
  • How does the page change? Where does the reason appear?
  • Which of the existing tests would fail?
Think about that last one The existing tests were "an empty name is rejected" and "an empty message is rejected". Would adding a banned-word check make those fail?

They should not. If they do fail, the new check has been put somewhere it interferes with the old one. That is worth finding before you approve the diff.

6.3.2Write the finish conditions

ConditionWho checks
1A message with a banned word is not postedA test
2A message without one is posted as beforeA test
3When refused, the reason appears on the pageA person looks
4Every existing test still passesA test

Do not forget number 2. Ask only for "block banned words" and an implementation that blocks everything also passes.

6.3.3Ask for it

PROMPTAdd a banned-word check to the Flask Vibe Chat. Requirements: - Keep a list of banned words in app.py - A message containing a banned word must not be added to the list - Show the reason on the page when a message is rejected - A message without banned words must still be added as before - Add a test for a rejected message - Add a test for an accepted message - Do not change the existing tests Edit app.py, templates/index.html and tests/test_app.py only. Keep the plan under 10 lines. Do not edit the file yet. Show the plan only.

6.3.4What to look for in the diff

CheckWhy
Is the empty-input check still there?Has it been replaced by the new one?
Is the word match case sensitive?Either is fine, but was it decided on purpose?
Where does the reason appear?Somewhere you can actually see it
Have the existing tests been changed?If so, ask why

6.3.5Check it

pytest

You should have four passing tests. The two from before, and the two from this change.

Then try both cases in the browser: a message with a banned word, and one without.

This is where Part 5 pays off You added a feature, and one command told you the existing behaviour still holds.

Without tests, this would mean checking sending, deleting, empty input and banned words by hand. Four checks after every single change. And the list only grows.

6.5What we know so far

You added one feature. pytest told you the existing behaviour was intact.

In Part 4 you checked Send and Delete by hand after every fix. Here the checking was one command.

Tests do not guarantee correctness A test can pass while the specification behind it is wrong, in which case the code is wrongly correct.

What goes in the banned-word list. What to show when a post is refused. Those are decisions a person makes. The tests only confirm that what you decided is still holding.
