7.1A minimal agent in plain Python

No frameworks yet. The loop is short enough to read in one go.

7.1.1Put limits on the tools

Before writing the loop, restrict what the tools can reach. An agent can only do what its tools allow.

Write the limits first, not later A write_file that takes any path can write anywhere on your machine. Adding a check afterwards is how you forget one.

_safe_path below refuses anything outside the project. Every tool goes through it. 
import subprocess
from pathlib import Path

PROJECT_ROOT = Path.cwd().resolve()


def _safe_path(path: str) -> Path:
    target = (PROJECT_ROOT / path).resolve()
    if PROJECT_ROOT not in target.parents and target != PROJECT_ROOT:
        raise ValueError("files outside the project are not allowed")
    return target


def read_file(path: str) -> str:
    return _safe_path(path).read_text(encoding="utf-8")[:4000]


WRITE_ROOTS = [PROJECT_ROOT, PROJECT_ROOT / "tests"]


def write_file(path: str, content: str) -> str:
    target = _safe_path(path)
    if not any(root == target.parent or root in target.parents
               for root in WRITE_ROOTS):
        raise ValueError("only the project root and tests/ may be written")
    if target.suffix != ".py":
        raise ValueError("only .py files may be written")
    target.write_text(content, encoding="utf-8")
    return f"updated {path}"


def run_tests() -> str:
    r = subprocess.run(
        ["pytest"],
        cwd=PROJECT_ROOT,
        capture_output=True,
        text=True,
        timeout=120,
    )
    return (r.stdout + r.stderr)[-4000:]


TOOLS = {"read_file": read_file, "write_file": write_file, "run_tests": run_tests}
LimitWhat it prevents
_safe_pathReaching outside the project, including via ../
WRITE_ROOTSWriting anywhere except the project root and tests/
.py onlyOverwriting configuration or data files
timeout=120A test run that never returns
[-4000:]A huge output filling the context

7.1.2The tool definitions and the loop

import ollama

MODEL = "qwen3.8:27b"

SCHEMA = [
    {"type": "function", "function": {
        "name": "read_file",
        "description": "read a file inside the project",
        "parameters": {"type": "object",
                       "properties": {"path": {"type": "string"}},
                       "required": ["path"]}}},
    {"type": "function", "function": {
        "name": "write_file",
        "description": "rewrite a .py file inside the project",
        "parameters": {"type": "object",
                       "properties": {"path": {"type": "string"},
                                      "content": {"type": "string"}},
                       "required": ["path", "content"]}}},
    {"type": "function", "function": {
        "name": "run_tests",
        "description": "run pytest and return the result",
        "parameters": {"type": "object", "properties": {}}}},
]


def agent(goal: str, max_steps: int = 12) -> str:
    messages = [{"role": "user", "content": goal}]

    for step in range(max_steps):
        reply = ollama.chat(model=MODEL, messages=messages, tools=SCHEMA)
        # depending on the library version this is an object or a dict.
        # normalise to a dict before using it.
        msg = dict(reply["message"])
        messages.append(msg)

        calls = msg.get("tool_calls") or []
        if not calls:
            return msg["content"]            # nothing proposed, so stop

        for call in calls:
            fn = dict(dict(call)["function"])
            name = fn["name"]
            args = fn.get("arguments") or {}
            try:
                result = TOOLS[name](**args)   # this is where it actually happens
            except Exception as e:
                result = f"error: {e}"
            messages.append({"role": "tool", "content": str(result)})

    return "stopped (reached the step limit)"


print(agent("Run pytest, find out why a test is failing, and fix it"))

7.1.3The core of an agent is in this loop

Of everything in this part, TOOLS[name](**args) is the line to remember. This is where a file gets read. Where it gets written. Where a command runs.

The model returned a string. Your code is what executes. When Part 1 said the model does not act directly, this line is what it meant.

Write the stopping condition yourself max_steps is the limit. Without it, a model that keeps proposing tools keeps being called. It will not stop on its own.

That costs money on a paid API, and on any API it means an agent editing files with nobody watching. If you build the agent, you write the stopping condition.
In the loopWhat it corresponds to
ollama.chat(...)Decide
TOOLS[name](**args)Execute
messages.append(...)Feed the result back
for step in range(...)Repeat, with a limit

Cline is doing the same four things, with a user interface around them.

7.2Connecting the pieces with LangChain

The plain loop works, but every piece is hand-wired. LangChain gives those pieces standard shapes.

7.2.1Six ideas in LangChain

7.2.2A small exercise: a travel suggestion in a fixed shape

Pulling specific fields out of free-form prose is difficult. The program below forces the output into four fields: name, region, how to get there, and what to see.

uv add langchain langchain-ollama pydantic
from pydantic import BaseModel, Field
from langchain_core.prompts import ChatPromptTemplate
from langchain_ollama import ChatOllama


class Destination(BaseModel):
    name: str = Field(description="name of the destination")
    region: str = Field(description="state or region it is in")
    access: str = Field(description="main way to get there from the city")
    highlight: str = Field(description="what makes it worth visiting")


prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a travel adviser."),
    ("human", "Suggest one destination about an hour from Mumbai."),
])

model = ChatOllama(model="qwen3.8:27b", temperature=0)
structured_model = model.with_structured_output(Destination)

# prompt -> model -> Destination, in that order
chain = prompt | structured_model
result = chain.invoke({})

print("destination:", result.name)
print("region:", result.region)
print("access:", result.access)
print("highlight:", result.highlight)

What to do with it

Run it, then change one thing and run it again. Change a description, add a field, or change the city in the prompt.

The point is that the output shape is fixed by your class, not by the wording of the reply.

7.2.3From a Chain to an Agent

A Chain runs in a fixed order. An Agent decides what to do next from the result.

ChainAgent
Order of stepsFixed when you write itDecided at run time
ToolsNot usedChosen by the model
RepeatsRuns onceLoops until a condition is met
Good forA known sequenceWork whose steps depend on what it finds
 
from langchain.agents import create_agent
from langchain_core.tools import tool
from langchain_ollama import ChatOllama


@tool
def read_file_tool(path: str) -> str:
    """Read a file inside the project. Path is relative to the repository root."""

7.3Designing the flow with LangGraph

Next, the shape of the work. Where it branches after a failure, how many retries are allowed, and where a human is asked.

7.3.1The flow you build

Solid lines are the normal path. The dashed line is the send-back from revise

The only place an LLM is called is implement. Everything else is ordinary Python.

uv add langgraph
import subprocess
from typing import TypedDict
from langgraph.graph import StateGraph, START, END

MAX_ATTEMPTS = 3


class State(TypedDict, total=False):
    goal: str
    attempts: int
    check_output: str
    passed: bool
    diff: str
    decision: str
    review_feedback: str


def plan(state: State) -> State:
    return {**state, "attempts": 0}


def implement(state: State) -> State:
    # the only agent call. reuses agent_executor from 7.2.
    prompt = state["goal"]
    if state.get("check_output"):
        prompt += f"\n\nPrevious run:\n{state['check_output']}"
    if state.get("review_feedback"):
        prompt += f"\n\nFeedback from the reviewer:\n{state['review_feedback']}"
    agent_executor.invoke({"messages": [("user", prompt)]})
    return {**state, "attempts": state["attempts"] + 1}


def check(state: State) -> State:
    r = subprocess.run(["pytest"], cwd=PROJECT_ROOT,
                       capture_output=True, text=True, timeout=120)
    return {**state,
            "check_output": (r.stdout + r.stderr)[-4000:],
            "passed": r.returncode == 0}


def route_after_check(state: State) -> str:
    if state["passed"]:
        return "review"
    if state["attempts"] >= MAX_ATTEMPTS:
        return "give_up"
    return "implement"


def give_up(state: State) -> State:
    print("Three attempts, still failing. Handing back to a human.")
    print(state["check_output"])
    return state
Not assembled yet The nodes and the branching are in place. Building the graph and calling compile() happens in 7.4, because review does not exist yet.

7.3.2Build the stopping condition into the design

MAX_ATTEMPTS is the retry limit. After three failures the agent stops and hands the result back to a person.

Retrying forever is a cost problem and a safety problem. If you build the agent, you write the stopping condition.

Why check is its own node Rather than letting the LLM claim it ran pytest, the graph runs it as a node every time. This is where turning your finish conditions into tests, back in Part 5, starts paying off.

The structure means the agent can only reach "done" when the check node returns success.

7.4Approval, interruption and resuming

The review node stops the run and waits for a human decision.

from langgraph.checkpoint.memory import MemorySaver
from langgraph.graph import StateGraph, START, END
from langgraph.types import interrupt, Command


def review(state: State) -> State:
    diff = subprocess.run(["git", "diff"], cwd=PROJECT_ROOT,
                          capture_output=True, text=True).stdout
    answer = interrupt({
        "diff": diff[:4000],
        "check_output": state["check_output"],
        "question": "Accept this change?",
        "choices": ["approve", "revise", "stop"],
        "when_revise": "Say what you want changed",
    })
    return {**state,
            "diff": diff,
            "decision": answer["decision"],
            "review_feedback": answer.get("feedback", "")}


def route_after_review(state: State) -> str:
    if state["decision"] == "revise":
        return "implement"   # send the feedback back and try again
    return END               # approve and stop both end the run

7.4.1Now assemble it

graph = StateGraph(State)
graph.add_node("plan", plan)
graph.add_node("implement", implement)
graph.add_node("check", check)
graph.add_node("review", review)
graph.add_node("give_up", give_up)

graph.add_edge(START, "plan")
graph.add_edge("plan", "implement")
graph.add_edge("implement", "check")
graph.add_conditional_edges("check", route_after_check)
graph.add_conditional_edges("review", route_after_review)
graph.add_edge("give_up", END)

app = graph.compile(checkpointer=MemorySaver())

config = {"configurable": {"thread_id": "task-001"}}
app.invoke({"goal": "Fix the failing pytest"}, config)
# -> stops at interrupt and returns the diff
# a human reads the diff, then resumes

app.invoke(Command(resume={"decision": "approve"}), config)

# if you want something changed
app.invoke(Command(resume={
    "decision": "revise",
    "feedback": "Fix the implementation, not the test",
}), config)

Choosing revise sends the run back to implement. The agent tries again using the previous test output and your feedback.

An approval mechanism needs a route back, and a way to carry the reason. Approve-or-nothing is not an approval mechanism.

MemorySaver keeps state in memory With a thread_id you can resume a paused run within the same Python process.

End the program and the MemorySaver state is gone. To resume on another day, use a durable checkpointer such as SQLite or PostgreSQL. For this exercise, pausing and resuming within a session is enough.
Put side effects after the approval Write any node containing interrupt() on the assumption that it re-runs from the top when resumed.

Put a write to the outside world before the approval and it happens again on every resume. Sending mail, charging a card, deleting a file: those go in a separate node after the approval.

Keeping nodes small is not only about readability.

7.4.2Where to put approvals

Put oneWhy
Before anything irreversibleDeleting, sending, publishing, charging. Always stop before something you cannot undo
When the blast radius growsStop when the number of files or lines changed passes a threshold
When the agent is stuckHanding back after three attempts is a correct ending, not a failure
When it reaches outsideNetwork calls, external APIs
