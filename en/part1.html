PART 1

How an LLM works, and where it fails

An LLM sits at the centre of a Coding Agent. On its own, though, it cannot even read a single file. This part covers what an LLM does as a component, and where and why it gets things wrong.

1.1What an LLM does

A large language model (LLM) is a very large neural network. It has been trained on an enormous amount of text.

What it does is simple. From the text so far, it picks the next word. Then it does that again.

Predict the next token and append it. Text and code come out of this loop alone

The smallest unit here is called a token. A token is often smaller than a word. "hello" is one token; "unbelievable" is usually three or four. Languages that do not use spaces, such as Japanese or Thai, are split differently again.

The LLM converts your input into tokens before it does anything else.

Out of this loop come translation, summarising, conversation and programming. Code is a particular strength, for two reasons. The format is strict, and there is a great deal of it in the training data.

1.1.1What it cannot do

This is the starting point. An LLM takes text and returns text. By itself it does nothing else.

It cannot
Read a file
Run a command
Know what is happening now (its knowledge stops at training time)
Check whether its own answer is correct

However capable it is, an LLM by itself never touches your codebase.

How you fill those four gaps is what a Coding Agent design is. Section 1.2 looks at the limits. Part 3 looks at how they are filled.

Models that show their reasoning Some models print their intermediate reasoning before the answer. Run ollama run qwen3.5:4b and you will see a long <think> block first. Nothing is stuck. Wait for it.

Do not treat that block as the model's real thinking. It is generated text like any other, and it sometimes contradicts the final answer. It is useful to read. It is not evidence.

1.2Context and error

Most of the trouble you will hit falls into two shapes. Either the input does not fit, or the answer is wrong and confident.

1.2.1The context window

An LLM has a context window. Think of it as working memory. The tokens in your input and its output together have to fit inside it.

The numbers move quickly. At the time of writing, some frontier models handle around a million tokens, and models you can run locally may support 200,000 or more.

But "supports it" and "you are actually using it" are different things.

Two traps 1. It does nothing unless you configure it.
When you run locally, the runtime's own default may be much smaller. A model may support 260,000 tokens, but without setting num_ctx you get the default. No error appears. History is silently dropped. (Appendix A, A.3.2)

2. Longer does not mean smarter.
Information in the middle of a long context tends to be used less reliably than what sits at either end. This is known as Lost in the Middle. Making the window longer does not remove it.

When a Coding Agent seems to forget a file it created earlier in a long session, this is one of the first things to suspect.

There are two responses. Summarise the history partway through, or hand over to a new session. You will do this in Part 6.

1.2.2Knowledge stops at training time

The model knows the world as it was when training finished.

Library APIs change. Patterns that have since been deprecated are still in the model. Newer versions are not.

That is where most "works, but written the old way" code comes from.

1.2.3Confident and wrong

Hallucination is when the model states something untrue as though it were fact.

"Tell me about the new programming language announced in August 2025."
→ "NeoScript rethinks JavaScript's asynchronous model from the ground up, and was developed jointly by Google and Meta..."
(No such language, and no such announcement)

The difficulty is the tone. A correct answer and a wrong one come back in exactly the same voice. Uncertainty is not displayed.

So bracing yourself against "AI lies" does not help much. A more useful reading: if you ask it to answer without giving it what it needs, it fills the gap with something plausible.

Back to Exercise 0 In Exercise 0 you named work for three countries. One of them was probably a country you know almost nothing about. The table still filled up.

What this section describes happened in your own hands, less than an hour ago.

That is why you were asked to mark *guess and [assumption: ...]. You will do the same thing to an agent's output for the rest of this course: separate what it actually checked from what it filled in.

The remedy is grounding: give the model accurate source material and make it answer from that.

There are two routes, RAG and tool use. Tool use is what Part 3 covers. Putting llms.txt next to the code in Part 6 is the same idea.

1.3Exercise: find the limits yourself

Reproduce sections 1.1 and 1.2 on your own machine. Reading and agreeing is not the same as watching it happen on your screen. About 20 minutes.

Opening a terminal and installing a model are covered in Setup. Do that first if you have not.

ollama run qwen3.5:4b

1.3.1Test 1: knowledge stops at training time

PROMPTUp to what point does your knowledge go? Then name one event that happened after that, and describe it.

The second half is the interesting part. Some models invent a plausible event. Others answer that they cannot know. Record which one you got, and what it said.

1.3.2Test 2: confident and wrong

PROMPTExplain how to use the quickload module in the Python standard library, with a code example.

There is no such module. You may still get a code example that looks like it would run.

Look at the tone of the reply. Could you tell it apart from a correct answer?

This is the point Wrong answers do not look wrong. Uncertainty is not displayed. That is why, from Part 4 onwards, you put machine checks around the model rather than inside it.

1.3.3Test 3: does an instruction at the top survive to the bottom?

Use the long documents provided. A rule appears only at the top, and a question comes at the very end.

There are five versions of the same document, at different lengths (experiment3/). Start with the shortest and work up, watching for where the rule stops being followed.

FileCharactersRough tokens
exp3_short.md~1,200~600
exp3_medium.md~2,100~1,000
exp3_long.md~3,400~1,700
exp3_xlong.md~6,900~5,700
exp3_xxlong.md~12,100~10,100

Three rules are stated at the top of each document.

1. Answer with exactly three bullet points. No more, no fewer.
2. Keep each point under 40 characters.
3. No preamble and no closing remark. Output only the bullets.

The question at the end asks how orders are handled during the lunch peak. The answer is near the middle of the document.

How to run it

  1. Start ollama run qwen3.5:4b in a terminal
  2. Open experiment3/exp3_short.md in VS Code
  3. Select all with Ctrl + A, copy with Ctrl + C
  4. Paste into the terminal and press Enter as it is
  5. Record whether the output follows the three rules
  6. Repeat with medium, long, xlong and xxlong
Do not add a question of your own The question is already at the end of the file. Paste and press Enter without adding anything.

If you type something like "answer the question above", that becomes the new ending. The distance between the rule and the question changes, so you are no longer testing the same thing.
If pasting misbehaves Some terminals execute the newlines while you paste a long text. If that happens, pipe the file in instead of pasting.

Get-Content exp3_short.md | ollama run qwen3.5:4b (PowerShell)
cat exp3_short.md | ollama run qwen3.5:4b (macOS / Linux)

This is more reliable. One line, and no paste accidents.

Watch whether the rules hold. They break down in stages. Record how it broke, rather than a yes or no.

StageWhat you see
1Three points, but one of them runs past 40 characters
2A preamble appears ("Sure, here is a summary...")
3Four points, or two
4Not a bullet list at all
5An answer unrelated to the question
6It answers from the start or the end of the document, not from the middle

If you see stage 6, that is Lost in the Middle. The centre of the context was dropped.

A shorter version of the same test Using a model configured with a small num_ctx, the same thing happens within a few exchanges. Setup is in Appendix A, A.3.2.

Which is the point: this is not the model being forgetful. There is simply a limit to how much fits. Change the setting and it happens sooner or later.

This is the same effect as a Coding Agent drifting away from a rule you set at the beginning of a long task.

1.4What we know so far

An LLM can produce code and prose. From the enormous amount of code it has seen, it can assemble something that looks like it works.

But it cannot check whether that code runs. It cannot open a file, run a test, or read an error message. The four limits from 1.1.1 are all still there.

In the next part you build something by talking to an AI. You get to feel the speed. You also get to see what is missing when the LLM is all you have.
