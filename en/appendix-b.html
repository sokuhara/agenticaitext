B.1What this appendix is

Parts 5 to 7 of this course were originally written against a Node.js and TypeScript build. The main text moved to Python for two reasons.

You cannot review code you cannot read. Part 2 made the point that if you cannot read the output at all, you cannot tell a correct answer from a confident wrong one. For a reader meeting TypeScript and React for the first time, that assumption does not hold.

Mixing languages costs a local model more. With a different language on the front and the back, it switches context constantly. In practice, a single language held together better.

That said, if you are introducing this into an existing TypeScript project, or you genuinely need React on the front end, the original build fits your situation better.

The shape of each part, how you write prompts, how you cut work into iterations, and how you use /selfcheck.md are the same either way.

B.3Equivalent of Part 5: hardening the monorepo

Three packages: frontend/ (React, Vite, Tailwind CSS, Playwright), backend/ (Hono) and aws/ (AWS CDK, cdk-nag).

PROMPT (/deep-planning)I want to harden the security of this npm workspaces setup. - Review the folder structure below and propose improvements for the security gaps you find. - frontend/ (React, Vite, Tailwind CSS, Playwright) - backend/ (Hono) - aws/ (AWS CDK, cdk-nag) - Add the following to strengthen the development environment. - GitHub Actions - actionlint / zizmor - Renovate (minimumReleaseAge required) - Husky + lint-staged - gitleaks

Running the plan creates configuration for Renovate, gitleaks, Husky and lint-staged, and updates the existing GitHub Actions workflows. Verify afterwards with /selfcheck.md.

In the original build, these were the fixes that turned out to be necessary.

  • The vulnerability check command was missing from CI/CD
  • Husky emitted a warning from deprecated syntax
  • Vulnerabilities reported by npm audit had to be resolved
  • Several CLI tools needed adding to the Dev Container setup

What to check is the same as 5.3.3 in the main text. Do local and CI use the same commands (all through npm scripts)? Are lint, format, test and typecheck all run in CI? Can you tell from the log which command failed?

B.3.1Verifying it runs

Check that the React application starts and renders in a browser, with no blank screen and no console errors. Then use curl to confirm the backend endpoints respond as expected.

B.4Equivalent of Part 5: implementation

B.4.1The shared package

In the original build, shared/ held TypeScript type definitions and Zod schemas used by both the front end and the back end. That only works because both sides are the same language.

The Python version gives that role to Pydantic models alone, and passes them to the front end through an OpenAPI schema.

After implementing, check quality with /selfcheck.md. In the original build, the type definitions and Zod schemas scored well on both test quality and code quality.

B.4.2Backend (Hono)

Hono is a light, fast web framework, easy to host on Cloudflare Workers or AWS Lambda. Its middleware also makes OpenAPI integration straightforward.

Before implementing, put Hono's published llms.txt on disk so the agent can refer to it.

mkdir -p docs/ref/hono
curl -o docs/ref/hono/llms.txt https://hono.dev/llms.txt
PROMPTBased on @/docs/design/implementation_plan_vibe_order.md and @/packages/backend/docs/design.md, work out an implementation plan for the backend/ package. Take a plan that advances steadily, checking quality in detail at each iteration. Where you are unsure how to use Hono, refer to @/docs/ref/hono/llms.txt.

In the original build, the agent was asked to score its own first plan out of ten. It gave itself 7.5 and listed improvements, including reconsidering the WebSocket integration. Working from that, the plan was refined into nine iterations.

Partway through, at around 70% context usage, the remaining iterations were written out to /docs/prompt/backend_continuation_iterations5-9.md and handed to a fresh session. That handover habit is the same as in the main text.

B.4.3Frontend (React + Vite)

Vite publishes an llms.txt as well.

mkdir -p docs/ref/vite
curl -o docs/ref/vite/llms.txt https://vite.dev/llms.txt

The original build proposed ten iterations, and sessions were switched at phase boundaries. In the end, 173 tests passed. It was also confirmed during implementation that .clineignore prevented .env from being created.

Context cost in an SPA React, Vite and Tailwind means touching several files to build one screen. A large cloud model handles that; a local 27B consumes context quickly and starts failing at diff edits.

That is why the main text uses server-rendered HTML. If you take the original build, expect to switch sessions more often.

B.5Equivalent of Part 6: release

AWS CDK in TypeScript, with cdk-nag for rule checks. cdk synth before deploying, GitHub Actions for CI/CD.

PROMPTRun npm run test -w @myapp/aws. Where deprecation warnings appear, look them up through MCP.

End-to-end tests use the JavaScript version of Playwright. Both the tests themselves and the habit of pasting terminal logs back for debugging are the same as in the main text.

Everything the main text says about MCP applies unchanged. MCP sits in a layer independent of both the model and the language.

B.6Which to choose

SituationRecommended
Your readers or students work mainly in PythonMain text (Python)
You run a mid-sized model locallyMain text (Python). A single language holds together better
You are adding this to an existing TypeScript projectOriginal build
A rich SPA is part of the requirementOriginal build
You can use a large cloud modelEither. The constraints loosen
Changing the language changes none of the practice Concrete requirements, automated tests, consistent conventions, guardrails, CI. None of those were needed because of Node.js, and none of them are needed because of Python.

They are needed because an LLM generates code probabilistically. Changing the stack does not remove any of them.
