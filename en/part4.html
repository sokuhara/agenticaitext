PART 4

Test it, then have it fixed

When an agent says the work is done, that is not evidence. You try it yourself, and where it falls short you have it fixed. No code is written in this part. You test, and you decide what to approve.

Previously
In Part 3, Cline read files, wrote them and ran commands to assemble an app. You saw how fast that is.
This part
You test the app from Part 3 yourself, and have Cline fix what you find. One full turn around the fix loop.
Next
Part 5 hands that checking to a machine, because a person doing it every time will eventually forget.

4.0What you do in this part

MISSIONTest the Vibe Chat you built in Part 3. Find one problem, have Cline fix it, and run the same test again.

Seven steps, in order

WhatWhoRoughly
1Choose one test (4.1)You5 min
2Do it in the browser (4.1)You15 min
3Write down the problem (4.2)You15 min
4Ask for a fix in Plan mode (4.3.1)Cline10 min

About an hour and twenty minutes. Six of the seven steps are yours. The agent investigates and edits. That is all.

What you need

The index.html from Part 3. Have it open in a browser.

If you finished the optional Delete feature in 3.4, use that version. It gives you two more tests to choose from.

Behaving as specified is not a defect Messages disappearing on reload is what you asked for in Part 3, when you said to keep them in a JavaScript array only. That is the specification working.

The same goes for messages not being shared between tabs. Neither of those is a bug. What you are looking for here is behaviour you did not ask for.

4.1Choose one test

Pick one from the list. You do not need to do them all. The aim is to take a single problem all the way round the fix loop.

What to do
1Leave User name empty and press Send
2Leave Message empty and press Send
3Type 1,000 characters and press Send
4Type <h1>Hello</h1> and press Send
5Create two messages and Delete the first
6Alternate Send and Delete several times

Items 5 and 6 only apply if you built the Delete feature in 3.4.

Do it with your own hands Type into the field, press the button, look at the screen. A person does this.

Do not ask Cline to test it for you. It can read the code and conclude that it should work. Whether it does is a different question, and only pressing the button answers it.

4.1.1Getting 1,000 characters

You do not need to type them. Copy any paragraph and paste it ten times. You only need to see whether it overflows, so the count does not have to be exact.

4.2Write down the problem

Three lines. The third one matters most.

Write
1What you did
2What actually happened
3What should have happened instead

4.2.1An example

I typed 1,000 characters into the message field and pressed Send.
The text overflowed outside the message card.
It should wrap inside the card.
The third line is yours to decide "What should have happened" is not something the agent can decide. Setting the specification is a human job.

Wrap the text? Truncate it? Refuse input beyond a certain length? Any of those can be right. Whichever you choose becomes the specification.

Say only "it overflows, fix it" and the agent decides for you. You then get a fix that was never what you meant.
If you cannot find a problem A 27B model often produces something more solid than you expect. Finding nothing wrong in all six is a normal outcome, not a failed exercise.

In that case, pick one thing you would like to improve. A timestamp on each post, a confirmation before delete, shortening very long names. Writing "what it should do" works exactly the same way.

4.3Have Cline fix it

4.3.1Ask in Plan mode

Switch to Plan before you send. The three lines from 4.2 go straight into the prompt.

PROMPTThe message layout breaks when I submit a very long message. Expected result: The text should wrap inside the message card. Inspect index.html and show a short plan. Edit index.html only. Do not change the current design or other functions. Do not edit the file yet.

The first line is what actually happened. Expected result is what should have happened. Replace both with your own.

Keep the last four lines Edit index.html only　limits the scope
Do not change the current design or other functions　prevents collateral damage
Do not edit the file yet　stops it building before you have read the plan

Each one is doing work. Drop one and you make room for changes you did not ask for.

4.3.2You judge the plan

Cline returns a plan. Read it before you go on.

CheckIf it is wrong
Is the change related to the problem?If it touches unrelated code, say so and ask again
Does it change anything besides index.html?If it plans another file, ask for a one-file approach
Does it break Send or Delete?If it rewrites them, ask why
Has it added something you did not ask for?A redesign or a new feature was not requested

If it looks right, switch to Act. If not, say what is wrong and ask for a new plan.

4.3.3You judge the diff

In Act mode, Cline shows you the change. Save or Reject is your call.

What the diff containsDecision
Only the change that was neededSave
A rewrite of the whole fileReject
An added external libraryReject
A feature removedReject
Do not press it without reading Pressing Save without looking makes the approval meaningless. Read what changes, then decide.

If you Reject, say why and ask again. That exchange is part of what you hand in.

4.3.4You re-test

After Save, reload the browser. Check three things.

1　Repeat the test you chose in 4.1

2　Check that Send still works

3　Check that Delete still works, if you have it

Do not skip 2 and 3. A change made in one place can break another, and you will not notice unless you look.

"Fixed" from the agent is not evidence The evidence is that you did the same thing and got a different result.

If it is not fixed, describe what happened and ask again. Go back to 4.3.1.

4.4What to hand in

Six items, in one file.

ItemWhat
BeforeA screenshot showing the problem
The problemWhat you did, what happened, what should have happened
The planWhat Cline proposed
Your decisionWhy you chose Save or Reject
AfterA screenshot showing it fixed
Re-testResults for the problem, Send and Delete
"Your decision" is the important one Why did you Save? Why did you Reject? One to three lines is enough.

"The diff was three lines of CSS in index.html and left Send alone, so I saved it."
"The plan was to redesign the whole page, so I rejected it and asked only for the wrapping rule."

That judgement is the thing this part is teaching.

4.4.1Who did what

Before you submit, look back at your own work.

WhoWhat they did
YouFound the problem. Decided what should happen instead. Read the plan. Approved the diff. Verified the result

The agent investigated and edited. Setting the specification, approving the change and verifying the result were all yours.

Submission is through the same peer evaluation system as Exercise 1. Use the Assignment 2 card.

4.5What we know so far

When an agent says "done", that tells you it finished, not that it works.

The evidence is that you operated it and looked at the result. In this part you did that by hand.

Are you going to do this every time? One fix took about an hour and twenty minutes. Operate, record, ask, read the plan, read the diff, operate again.

Can you repeat that for every change? Will you remember, every time, to check that Send and Delete still work?

Probably not, and not because you are careless. Checking the same three things after every change is exactly the kind of work people stop doing. So you hand it to a machine.

Part 5 automates this checking. Anything a machine can judge, such as "Send works" or "Delete works", becomes a test.

Deciding what should happen, and approving a diff, cannot be automated. Those stay with you.
