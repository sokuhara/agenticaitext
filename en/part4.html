このアプリ、本当に提出できる？

Agentが「完成しました」と言っても、それは完成の根拠になりません。自分で操作して確かめ、問題があれば直させます。この章ではコードを書かず、テストと承認の判断だけを行います。

PART 3で、Clineが自分でファイルを読み書きし、コマンドを実行してアプリを組み上げました。速さは体験できたはずです。

4.0この章で何をするか

MISSIONPART 3で作った Vibe Chat を、6項目すべてテストしなさい。 見つかった問題から1つ選び、Clineを使って修正し、同じテストをもう一度行いなさい。

3つの作業を順に行います

やること誰が目安
16項目のテストを実行させる（4.1）Cline10分
2報告を読み、だめだった項目を自分でも再現する（4.1）人間10分
3直す1件と、本来どうなるべきかを決める（4.2）人間15分
4Planモードで修正を依頼する（4.3.1）Cline10分
5Planを判断する（4.3.2）人間10分
6差分を判断する（4.3.3）人間10分
7再テストする（4.3.4）人間15分

およそ1時間20分です。7つのうち5つが人間の作業です。Agentがやるのは、試すことと直すことだけで、判断はしません。

使うもの

PART 3で作った index.html です。ブラウザで開ける状態にしておいてください。

3.4のDeleteボタンまで実装した版を使います。終わっていなければ、先に3.4を終えてください。Deleteがないと、6項目のうち2つが試せません。

始める前に index.html を複製して work_before_part4.html という名前で保存しておきます。壊したときに戻すためです。

作業しながら残すもの

提出するのは index.html 1本です。修正後のファイルの末尾に、次の4つをコメントとして書き足します（4.4）。あとから作れないものが多いので、その手順に来たときに控えておいてください。

残すもの内容いつ
テスト結果だめだった項目の番号（自分で再現できたもの）4.1
問題の記録操作、実際の結果、本来どうなるべきか4.2
PlanClineが出した計画を1つだけコピーしておく。出し直させた場合はどれでもよいが、次の「判断」はこのPlanについて書く4.3.1
人間の判断上のPlanに対して、進めたかRejectしたか、その理由（1〜3行）4.3.2
「人間の判断」がいちばん重要です なぜSaveしたのか。なぜRejectしたのか。判断は何回もしますが、書くのは提出するPlanに対する1回だけです。Planと判断が対になっていないと、読む側には分かりません。1〜3行で構いません。

「差分がindex.htmlのJS数行だけで、Send機能に手を入れていなかったのでSaveした」
「入力欄そのものを作り直す計画だったのでRejectし、200文字の判定だけを頼み直した」

この判断が、この章で身につけるものです。
仕様どおりの動作を欠陥と呼ばないこと 再読み込みで投稿が消えるのは、PART 3で「JavaScript配列だけに保持する」と指示したからです。仕様どおりです。

複数のタブで共有されないのも同じです。これらは不具合ではありません。この章で探すのは、指示していないのに起きてしまう問題です。

4.16項目をすべて試させる

次の6項目を、Clineにすべて実行させます。Clineはブラウザを開いて操作し、結果を報告します。1つずつ選んで試すのではなく、全部です。

Act モードで、次をそのまま送ります。ブラウザを開く操作の承認を求められたら承認します。

PROMPTOpen index.html in the browser and run these six tests one by one. For each test, report three things: what you did, what the page showed, and whether it looks wrong. Do not edit any file. 1. Send with an empty user name 2. Send with an empty message 3. Send a message of about 1000 characters (spec: a message is at most 200 characters; longer ones must be rejected with an error) 4. Send the message

Hello

5. Send two messages, then click Delete on the first 6. Alternate Send and Delete several times and check the message count each time Finish with a list of the test numbers that look wrong.
操作
1User name を空欄にして Send
2Message を空欄にして Send
31000文字を入力して Send。仕様：メッセージは200文字まで。超えたら送信せず、エラーを出す
4<h1>Hello</h1> を入力して Send
5メッセージを2件作り、1件目を Delete
6Send と Delete を何度か繰り返す
3は、ほぼ全員がだめになります 「200文字まで」は、PART 3のプロンプトでは指示していない仕様です。だから今のアプリは、長い文章をそのまま受け付けます。仕様として決めた瞬間に、それは不具合になります。

これで、直す1件が必ず1つはあります。ほかが全部問題なくても、この章は先へ進めます。
何を「おかしい」と呼ぶかは、あなたが決めます 空欄で送れてしまう、200文字を超えても送れてしまう、タグがそのまま効く、別のメッセージが消える、件数が合わない。こうしたものです。

迷ったら控えておき、4.2で「本来どうなるべきか」を考えるときに判断してください。
報告は根拠ではありません Clineが「おかしい」と言った項目は、自分の手でも同じ操作をして確かめます。「問題なし」と言った項目のうち、少なくとも3は自分でも試します。

Agentはコードを読んで「動くはずだ」と結論することがあります。動いたかどうかは、画面を見た人だけが言えます。ここで控えるのは、あなたが再現できた項目です。

4.1.1自分で再現するときの1000文字

手で打つ必要はありません。適当な文章をコピーして、10回ほど貼り付けてください。200文字を超えたときに何が起きるかが分かればよいので、正確に1000文字である必要はありません。

4.2直す1件と、本来どうなるべきかを決める

4.2.01件を決める

4.1で控えた項目から、この章で直す1件を決めます。

控えた項目選ぶもの
複数あるいちばん気になるもの1つ
3だけ3（文字数の上限）

27Bが作ったものは意外としっかりしていて、だめだったのは3だけ、という結果がいちばん多いはずです。それで構いません。

4.2.1本来どうなるべきかを決める

1と2は4.1で分かっています。この節で決めるのは3だけです。3つを並べると、4.3.1でClineに送る文になります。

内容どこから
1行った操作4.1の項目
2実際に起きたこと4.1で見たこと
3本来どうなるべきかここで決める

4.2.2並べた例

メッセージ欄に1000文字を入力してSendを押した。
そのまま投稿された。
200文字を超えるメッセージは送信されず、エラーが表示されるべきである。
3番目は、あなたが決めます 「本来どうなるべきか」は、Agentには決められません。仕様を決めるのは人間の仕事です。

「200文字まで」は決まっていますが、その先は決まっていません。Sendを押したときに弾くのか、入力欄に201文字目を打てなくするのか、残り文字数を表示するのか、エラーの文言は何か。どれも正解になりえます。あなたが選んだものが仕様になります。

ここを書かずに「長くても送れます、直して」とだけ伝えると、Agentは勝手に決めます。意図と違う直し方をされます。

4.3Clineに修正させる

4.3.1Planモードで依頼する

Plan に切り替えてから送ります。4.2で書いた3つを、そのまま英語にします。

PROMPTA message longer than 200 characters is accepted and posted as is. Expected result: Messages longer than 200 characters must not be sent. Show an error message below the input instead. Inspect index.html and show a short plan. Edit index.html only. Do not change the current design or other functions. Do not edit the file yet.

上から3行目までが実際に起きたこと、`Expected result` が本来どうなるべきかです。あなたの記録に合わせて書き換えてください。

最後の4行は必ず入れます Edit index.html only　変更範囲を限定する
Do not change the current design or other functions　巻き添えを防ぐ
Do not edit the file yet　Planを読む前に実装させない

1つ抜けるだけで、余計な変更が混ざります。

4.3.2Planを人間が判断する

Clineが計画を出します。読んでから次へ進みます。

確認すること問題があったら
問題と関係のある変更か関係ない箇所を触る計画なら、指摘して出し直させる
index.html 以外を変更しないか別ファイルを作る計画なら、1ファイルで済む方法を求める
SendやDeleteを壊さないか書き換える計画なら、理由を確かめる
不要な機能を追加していないかデザインの刷新、新機能は頼んでいません

問題がなければ Act へ切り替えます。問題があれば、その場で指摘して計画を出し直させます。

4.3.3差分を人間が判断する

Actにすると、Clineが変更を提示します。SaveかRejectかを、あなたが選びます。

差分の中身判断
必要な変更だけSave
全体を書き直しているReject
外部ライブラリを追加しているReject
別の機能を削除しているReject
差分を見ずに押さないこと 見ずにSaveを押していると、承認の意味がありません。何が変わるのかを読んでから決めてください。

Rejectしたら、理由を書いて出し直させます。そのやり取りが提出物になります。

4.3.4人間が再テストする

Saveしたら、ブラウザを再読み込みします。確認するのは3つです。

1　4.2で決めた操作を、もう一度行う

2　Send が今までどおり動くか確認する

3　Delete が今までどおり動くか確認する（実装している場合）

2と3を飛ばさないでください。直したつもりで、別のところを壊していることがあります。

Agentの「修正しました」は根拠になりません 根拠になるのは、あなたが操作して結果が変わったことだけです。

直っていなければ、何が起きたかを伝えて再修正させます。4.3.1へ戻ってください。

4.5この章で分かったこと

Agentが「完成しました」と言っても、それは完成の根拠になりません。

4.1でClineにテストさせました。報告は速く返ってきますが、それをそのまま信じることはできず、結局あなたが再現しました。直したあとも、Sendが動くか、Deleteが動くかを、また自分で確かめました。

たくさん頼めば速いわけではありません 6項目を一度に頼んでも、報告のどこまでが本当かは、人間が確かめるまで分かりません。頼む量を増やすほど、確かめる量も増えます。

「全部やっておいて」と投げて、返ってきた報告を読み、疑い、再現し、直させ、また確かめる。その時間は、Agentが速くなっても減りません。

減らす方法は1つです。確かめる作業そのものを、報告ではなく判定にする。「Sendが動く」を人が見るのではなく、機械が合否を出すようにします。

PART 5では、この確認を自動化します。「Sendが動く」「Deleteが動く」のように機械が判定できるものは、テストになります。

一方で、「本来どうなるべきか」を決めることと、差分を承認することは自動化できません。それは人間に残ります。
