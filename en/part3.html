3.1Exercise: let Cline build an app

Exercise 1 in Part 2 changed things that already existed, by name. You did the moving. Here the agent builds from nothing.

What it builds, though, is deliberately small. A single HTML file, no server, no database.

What this exercise is for Not "did you produce an impressive app". Did you watch an agent read files, write them and run commands.

Ask for more and the experience changes. Instead of "the agent did some work" you get "the environment kept breaking". That is why databases, authentication, real-time messaging and containers are all excluded.
The whole exercise Work down the list. Do not skip steps.

What Plan mode is for Plan mode is for agreeing, before anything is built, on what to make, which files to create, and how you will check it.

The goal at this stage is not to get files created. Cline may read the folder or ask you questions. That is it gathering what it needs for the plan.

PROMPTCreate a simple one-page message board in one file named index.html. Requirements: - User name input - Status select: Present, Away, Focus - Message input - Send button - Submitted messages appear below the form - Keep messages only in a JavaScript array - Reject empty user names and messages - Use textContent to display user input - Put HTML, CSS, and JavaScript in index.html Do not use: - Python - Node.js - React - Database - WebSocket - Fetch - Polling - External libraries - Multiple files The workspace is empty. Do not inspect it. Keep the plan under 10 lines. Do not create or edit files yet. Show the plan only.

This part builds index.html only, so that you can concentrate on operating a coding agent. A Python and Flask web app comes in a later part.

The list of exclusions matters. Without it, the agent tends to be helpful and add a server, a database, real-time messaging and several files. Every one of those is another thing that can break in front of you.

Read the plan

Cline replies with an implementation plan. Do not switch to Act yet. Stop and read it.

  • Is index.html the only file it will create?
  • Does it put the HTML, CSS and JavaScript in that one file?
  • Does it keep messages only in a JavaScript array?
  • Does it use textContent for user input?
  • Has anything crept in: Python, Node.js, an external library?

If something extra appeared, or a needed check is missing, ask for a fix while still in Plan mode.

PROMPTRevise the plan to follow the requirements exactly. Use only one file: index.html. Do not add any unrequested features. Show the revised plan only.

Read the revised plan before moving on. Repeat until you are satisfied with it.

When the plan is done The plan is finished when you can answer these four in your own words.

1. What are we building? 2. Which files? 3. Where does the data live? 4. What will make it finished?

Two things that go wrong in Plan mode

Switching to Plan does not guarantee a good plan. Both of these are common in this exercise.

Failure 1: it keeps checking the folder Cline may propose Get-ChildItem and similar listing commands over and over, each time worded slightly differently. If it already knows the folder is empty, another listing tells it nothing new.

Reject it because the purpose is duplicated, not because of the number of attempts, and tell it to stop.
PROMPTThe workspace is empty, and directory inspection is complete. Do not run any more directory-listing commands. Now show the implementation plan only. Do not create or edit files yet.
Failure 2: one file turns into a system Even when you specify index.html only, Cline may come back with a plan involving package.json, server.js, Express, React, WebSocket or a Python server.

A detailed, convincing plan is not necessarily a plan that follows your request. Do not move to Act. Shrink it back while still in Plan mode.
PROMPTThis plan does not follow the requirements. Use only one file: index.html. Put the HTML, CSS, and JavaScript in that file. Store messages only in a JavaScript array. Do not use Python, Node.js, Express, React, Vite, WebSocket, fetch, polling, a database, or external libraries. Keep the revised plan under 10 lines. Do not create or edit files yet. Show the revised plan only.
This is why Plan mode exists Run a bad plan in Act mode and you get files and packages you did not want. In Plan mode, a human can spot the drift and correct it before a single file changes.

3.2Why the same request gives different results

You have just seen the result change with the way you asked. Agents do not only fail because they are not capable enough. They also fail when they were not given what they needed.

Ask only "fix the login screen" and the agent does not know:

  • Which screen you mean
  • What it is allowed to change
  • What the existing design rules are
  • What to check once it is done

Left without those, it produces something plausible. The confident wrong answer from Part 1, section 1.2.3, arriving as code.

Context engineering means giving the right information at the right moment, so the agent can make a decision.

It does not mean handing over a long document all at once.

3.2.1Four kinds of context

KindExample
The goal"Validate the email address format"
Constraints"Do not change the existing API." "Keep the change minimal."
Project rulesCoding conventions, which libraries, how to run tests
Current stateThe file in question, error logs, test results, open issues

3.2.2How you hand it over changes the result

This instruction gives only the goal.

POORFix the validation.

With all four, the agent can decide.

BETTERFix the email validation in src/user.py. Do not change the API return values. Make the failing tests in tests/test_user.py pass, and run the existing tests too. Before editing, briefly explain the cause and what you intend to change.

Line 1 is the target, line 2 the constraint, line 3 how to verify, line 4 how to proceed. Same request, different handover, different result.

More information is not automatically better Stale specifications, piles of unrelated files, contradictory instructions. All of them make the agent's judgement worse.

As section 1.2.1 showed, context is finite and the middle gets dropped. Give what is needed, in the amount needed, without contradictions.

3.3How much to delegate

Coding agents suit work where the conditions are clear and the result can be checked.

The opposite does not suit them: vague conditions, and results no machine can verify.

Easy to delegateNeeds a human
Finding related filesDeciding what to build
Working out how existing code is structuredOrdering the requirements
Implementing a small featureChoosing the design approach
Adding and running testsDeciding the scope of a change
Reading an error and trying a fixApproving a release to production
Routine refactoringJudging security, legal and user impact

3.3.1What "delegate" means

It does not mean letting it run unchecked.

You start by giving the agent a narrow area. For example:

  • It may only change things inside this folder
  • Running tests is allowed; sending anything outside is not
  • Config files and credentials are off limits
  • Changes go through a pull request, never straight in

From Part 4 onwards you widen that area safely, using tests, linters, CI and approval steps.

Deciding to widen it, though, stays a human job to the end.

3.3.2Degrees of autonomy

Autonomy is not on or off. It comes in steps.

As you read, think about which step each of your three jobs from Exercise 0 would need.

StepThe machineThe humanWhere it appears here
CompletionPredicts the next few linesConstantly. Accepts line by line—
ChatAnswers and shows codeCopies, pastes, runsExercise 1, Part 2
CopilotProposes concrete changesApproves one at a time—
AgentPlans, uses tools, executes, checks its own result, repeatsSets the goal, approves at key points3.1, and Part 5 onwards
AutonomousTakes a request and runs to completionLooks only at the resultNot covered

Further down the table is faster. Further down also means a mistake is likely to reach you later, and larger.

Part 2 and this part are the speed. Part 4 counts the cost. Part 5 onwards puts approval and tests back in. The shape of this course is a movement up and down that table.

3.3.3The basic loop when using an agent

The flow you just went through, with names attached.
PlanSettle the goal, the scope and how you will check. Do not let it edit yet
ActLet the agent search, implement and run tests
ReviewLook at the diff, the test results, and anything changed that should not have been
Accept or RejectA human decides whether to take the change or keep working

Plan, Act, Review, Accept or Reject. These are not buttons in one product. They are the working procedure underneath.

The same holds in Cline, in a command-line agent, and in whatever tool replaces both.

Agents come in three shapes Built into an editor (Cline, Cursor). Used from a terminal (Claude Code). Running independently in the cloud (Devin, Jules).

They look and feel different. The loop in 3.5 and these four steps are the same in all of them. This course uses Cline.

3.4Optional: add a delete feature

TASKAdd the following to the Vibe Chat you built in 3.1. Put a Delete button on every message. Pressing it removes only that message and updates the count. Edit index.html only. Keep the current design and the Send feature.
What is new here The agent reads an existing file. It proposes a change. A human reads the diff and approves. A human checks the result in a browser. If it is wrong, the agent fixes it again.

That cycle is what we mean by the agent loop.

3.4.1A hint

Write your own instruction first. If you get stuck, this is a starting point. Begin in Plan mode.

PROMPTImprove the existing Vibe Chat in index.html. Add one Delete button to each displayed message. When clicked, delete only that message and update the message count. Requirements: - Edit index.html only - Preserve the current design and existing Send behavior - Keep messages only in the existing JavaScript array - Use textContent for user-provided text - Do not use external libraries, storage, fetch, or additional files - Keep the plan under 8 lines Do not edit the file yet. Show the plan only.

Reading the plan

  • Is index.html the only file it changes?
  • Does it keep the current design and the Send behaviour?
  • Does it update the count after a delete?
  • Has it added an external library or another file?

3.4.2What counts as finished

All of the following, checked in a browser.

  1. Press Ctrl + R to reload
  2. Send two messages
  3. Press Delete on the first one
  4. Check that only the first disappears
  5. Check that the second is still there
  6. Check that the count goes from 2 to 1
  7. Check that you can still send a new message
Delete working while Send is broken is a fail Do not check only Delete. Check Send as well. Agents sometimes break a feature you never asked them to touch.

3.4.3If it does not work

Tell Cline what actually happened. Delete does nothing, the wrong message vanishes, the count does not change, and so on.

PROMPTI created two messages and clicked Delete on the first message. The first message did not disappear, and the count stayed at 2. Inspect index.html and fix only this problem. Do not redesign the page or add files. After editing, tell me exactly what changed.

Read the diff, Save, then run the same test again. The test result feeds the next fix. That is the agent loop.
1ReadThe agent reads the existing index.html
2DecideIt works out what to change in the array and the rendering
3ProposeCline shows the diff with Save / Reject
4ExecuteYou press Save and Cline writes the file
5ObserveYou try Delete and Send in the browser
6CorrectYou feed the failure back, and it returns to step 2 if needed

3.4.4Who did what

WhoWhat they did in this task
The LLMProposed reading the file, and proposed the change for the delete feature

The model did not write the file The LLM proposes operations. Cline performs them. With auto-approve off, nothing runs until a human approves it.

3.5What we know so far

Cline takes a goal. It reads files and proposes changes. Once you approve, it writes the code. You no longer copy and paste anything.

What you built is practice. Reload the page and the data is gone. Two people cannot share it. There are no automated tests.

Working is not the same as usable An app that runs and an app you would hand to someone else are different things. Part 4 measures that distance on the app you just built.
