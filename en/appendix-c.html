C.1What this appendix covers

Carried over from the main text Whatever you choose from here on, these five do not change.

1. Nothing moves on until pytest passes (Part 5)
2. End-to-end tests are needed on top of unit tests (C.5)
3. Deployment credentials are kept separate from your own (C.2)
4. Secrets never go in the repository (Part 5)
5. Operations needs logs, cost visibility and a way to stop (C.6)

This appendix covers putting the application you built somewhere real, checking it works, and deciding whether to publish it.

C.1.1Only the sequence is universal

Wherever you deploy, the order is the same.

build -> verify -> deploy -> end-to-end check -> release decision

The sequence is the only thing that carries over. The artefact format, authentication, networking, where data lives, monitoring, and how you roll back all differ considerably between targets. Treating them as interchangeable is where projects lose time.

C.1.2Pick one standard route

RouteWhat it needs
StandardDocker ComposeDocker only. No cloud account, no billing
ExtendedAWS (CDK for Python)An AWS account, OIDC setup, role design
ExtendedA PaaSAn account with that service

For a class or a lab, make Docker Compose the standard. Students can run it locally, the way the app is served stays visible, and it carries all the way to end-to-end tests. A Dockerfile and a compose.yaml written by an agent are also good review material.

Why AWS is not in the main text Publishing on AWS means students spend their time not on Python and not on agentic coding, but on IAM permissions.

That is genuinely important knowledge. It is not what this course is for. For the AWS route, see C.4.2 onwards.
What containers are and are not for Docker is a way to package software and make environments consistent. It is not a requirement for agentic AI. To run FastAPI locally, uv run uvicorn is enough.

A Dev Container is the same: a tool for reproducible development environments. It is not a box that safely contains an agent. Mount the Docker socket or a broad host directory and the agent reaches straight outside it.

Control permissions through the permissions you grant, not through the container.

C.2Preparing the deployment environment

C.2.1Separate the deployment credentials

On AWS, you set up the CLI and grant permissions before an agent can build or change infrastructure. You are about to hand an agent strong permissions. Apply the "what to protect" decision from Part 4 here, for real.

Credentials you hand to an agent Use a dedicated set of deployment credentials, not your own.

Agents do misread instructions. What can be destroyed when one does is set entirely by the permissions you handed over.

C.3Implementing the deployment

From here you can connect the agent to external sources through MCP.

Connecting external tools MCP is one way to connect an agent to a browser, documentation or a database. It is not a deployment technology.

Enable only what you need, and only connect servers you trust. See section 6.5 in Part 6.

C.3.1Planning the implementation

Have the agent draw up a plan with the design documents in front of it.

PROMPTBased on @/docs/design/implementation_plan.md and @/docs/design/deploy.md, work out an implementation plan for the deployment setup.

On the standard route this is where the Dockerfile and compose.yaml appear. You may let the agent write them, but read the generated configuration yourself.

Health checks, published ports, how environment variables are passed, the scope of volumes. Approve those without reading and you can expose more than you intended.

# compose.yaml (skeleton)
services:
  app:
    build: .
    ports: ["8000:8000"]
    environment:
      - APP_ENV=staging
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8000/api/health"]
      interval: 10s
      retries: 5
Extended: deploying to AWS Lambda FastAPI is an ASGI application, so a few lines of CDK will not make it run. You need an adapter such as Mangum, or the Lambda Web Adapter, or to ship it as a container image. Dependencies also have to be packaged for Lambda's Linux environment.

Python 3.12 is available on Lambda, but "write a bit of CDK and it goes live" is not accurate. If you teach this, budget a full session for it.

C.3.2Checking before you deploy

Once implemented, confirm the definitions resolve before deploying anything.

uv run cdk synth        # check the CloudFormation template generates

# or

docker compose config   # check syntax and variable expansion
docker compose up --build   # bring it up locally once

C.4Deploying

Now you build the CI/CD that performs the deployment, and run it through GitHub Actions. You are adding a deploy job to the CI workflow from Part 5.

C.4.1Designing the pipeline

Keep verification and deployment separate, so that only what passed verification proceeds to deploy. Making the deploy a manual trigger rather than automatic limits the blast radius of a mistake.

C.4.2Implementing the pipeline

# .github/workflows/deploy-staging.yml
name: Deploy staging
on:
  workflow_dispatch:

permissions:
  contents: read
  id-token: write

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-python@v6
        with:
          python-version: "3.12"
      - uses: astral-sh/setup-uv@v6
      - run: uv sync --locked
      - run: pytest
      - uses: aws-actions/configure-aws-credentials@<pinned commit SHA>
        with:
          role-to-assume: ${{ vars.AWS_DEPLOY_ROLE_ARN }}
          aws-region: ap-northeast-1
      - run: uv run cdk diff
      - run: uv run cdk deploy --require-approval never
permissions alone does not authenticate id-token: write only grants permission to issue an OIDC token. Without the step that assumes the limited role on the AWS side (configure-aws-credentials), the deploy will not go through.

GitHub Actions OIDC exists so that you do not keep long-lived AWS keys in Secrets, and use short-lived credentials per run instead. Narrow the role's trust policy to the repository and the branch.

gitleaks, added in Part 5, is a last net for a key that got committed by accident. Designing so the key is never there in the first place comes first.

C.4.3Verifying the pipeline

Once designed and implemented, have the agent verify it. Use actionlint and zizmor to lint the workflow itself.

C.4.4Pull requests and CI checks

Open a pull request on GitHub and let the checks run.

A failing check blocks the merge. That is what branch protection does

When a deprecation warning or a test failure appears, use the MCP server you connected in Part 6 and have the agent find the cause.

PROMPTRun pytest. Where a DeprecationWarning appears, look up the currently recommended usage through MCP before fixing it.

C.4.5Running the deployment

Once the checks pass, run the deployment from "Run workflow" in GitHub Actions.

When make check stops, every later deploy step is skipped

When the check step stops, none of the later steps run. That is the whole point of putting verification before deployment.

C.5Checking after deployment

C.5.1Writing end-to-end tests

To confirm it works in a real environment, build end-to-end tests with Playwright. Playwright has a Python version with a pytest plugin.

Do not run end-to-end tests for the first time in production The order is: local → CI → deploy to staging → end-to-end on staging → human approval → production.

If production is the first place you run them, your users see the failures before you do.

When you write them, follow these.

  • Switch BASE_URL through an environment variable. Do not hard-code a URL
  • Create test data inside the test, and delete it afterwards
  • Save a screenshot and a trace on failure
  • Never use production data or a real user's account
  • If sign-in is needed, use a dedicated test account with its own permissions
uv add --dev pytest-playwright
uv run playwright install chromium
# tests/e2e/test_message_flow.py
def test_send_message(page):
    page.goto("http://localhost:8000/")
    page.fill("input[name='name']", "Asha")
    page.fill("input[name='message']", "Hello")
    page.click("button[type='submit']")
    assert page.locator("#message-list li").count() > 0

C.5.2Debugging end-to-end tests

When a test fails, paste the terminal output straight into the instruction.

PROMPTDebug why the end-to-end test does not run. @terminal

Most end-to-end failures are not implementation bugs. They are the test failing to set up its own preconditions. Redirect handling and role permissions are common causes.

C.5.3More tests, and fixes

Add end-to-end tests for each flow in turn, and work iteratively until they all pass.

Not finished until the end-to-end tests pass Part 5 mentioned tests passing while the page is broken. The usual cause is too much mocking.

All the unit tests being green does not mean the implementation is done. One passing end-to-end test does.

C.6Before a commercial release

Once the application runs, these are what you prepare for real operation. The list is the same whether you deploy to a cloud or to containers.
Multiple environmentsSeparate production from staging and development, and configure each
Monitoring, logs, alertsMetrics, how much log detail to keep, automatic alerting
SecurityA WAF, secrets held outside the repository, least privilege
Performance and costCost alerts, caching
OperationsAn incident runbook, automated maintenance and patching
Dependency updates are part of operations Automated dependency updates, such as Renovate, start earning their place here. An agent pins the dependencies as they were when it wrote the code. Somebody has to update them after that.

The "outdated dependency" problem from Part 1 is not only a problem while you are building. Left alone, it arrives on its own.
