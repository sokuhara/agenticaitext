3.1演習：Clineにアプリを作らせる

PART 2の演習1は、既にあるものを名前で変える作業でした。手を動かしたのはあなたです。

ここでは、何もないところからアプリを作らせます。ただし、作るものは意図的に小さくします。

この演習で見たいもの 「立派なアプリができたか」ではありません。Agentがファイルを読み、書き、コマンドを実行する過程を観察できたかです。

要求を大きくすると、体験する内容が変わります。「Agentが仕事をした」ではなく、「環境が壊れ続けた」になります。

だからデータベース、認証、リアルタイム通信、コンテナは全部外します。
この演習の全体像 上から順に、飛ばさずに進めてください。

フォルダを作る → VS Codeで開く → Clineを入れる → サーバに接続 → 接続テスト → Planモードにする → 課題を送る → 計画を確認 → 承認方法を先に確認 → Actへ切り替える → 1件ずつ承認 → ブラウザで開く → 動作確認 → 記録を残す

Continueを押すと Configure your provider の画面になります。既定は OpenRouter です。

OpenRouterのままだと、Base URLを入れる場所がありません。Model の欄に anthropic/claude-sonnet-5 などが入っていたら、消して入れ替えます。

https://pc11.okuharalab.com/v1 と、末尾まで入れてください。

3.1.6Planモードにしてから課題を送る

送る前にモードを変えます Clineの入力欄の右下に Plan / Act の切り替えボタンがあります。先に左側の Plan を押してください。Actが青く選択されたまま送ると、計画を見る前に実装が始まります。

Planモードへの切り替え方

  1. VS Code左側のClineアイコンを押し、Clineのチャット画面を開く
  2. 画面下部のメッセージ入力欄を見る
  3. 入力欄の右下に並んでいる Plan と Act を見つける
  4. 左側のPlanを1回押す
  5. Plan側に色が付き、Act側の色が消えたことを確認する
Planモードでは何をさせるのか Planモードは、実装前に何を作るか、どのファイルを作るか、何を実行して確かめるかを相談するために使います。この段階では、ファイルを作らせることが目的ではありません。

Clineがフォルダの中を読んだり、質問を返したりすることはあります。これは計画に必要な情報を集めている動作です。

この章では、Coding Agentの基本操作に集中するため、index.htmlだけを作ります。PythonとFlaskを使うWebアプリは、次の独立課題で扱います。

禁止事項が重要です。書かないとAgentは親切にサーバ、データベース、リアルタイム通信、複数ファイルを追加し、演習が長くなります。

計画を読む

プロンプトを送ると、Clineが内容を整理して実装計画を返します。ここではまだActへ切り替えず、一度止めて計画を読んでください。

  • 作るファイルが index.html の1つだけか
  • HTML、CSS、JavaScriptをその1ファイルに入れる計画か
  • メッセージをJavaScriptの配列だけに保存するか
  • ユーザー入力の表示に textContent を使うか
  • Python、Node.js、外部ライブラリなどが入っていないか

計画に余計なものが入っている、または必要な確認が抜けている場合は、Planモードのまま修正を頼みます。

計画を直すときの例Revise the plan to follow the requirements exactly. Use only one file: index.html. Do not add any unrequested features. Show the revised plan only.

すぐにActへ移らず、修正後の計画をもう一度読みます。計画に納得できるまで、このやり取りを繰り返してください。

Plan完了の判断 次の4点を自分の言葉で答えられたらPlanは完了です。①何を作るか、②作るファイルは何か、③データをどこに置くか、④何をもって完成と判断するか。

Planモードで実際に起こりやすい失敗

Planモードにしただけで、必ず正しい計画が出るわけではありません。次の2つは、今回の演習でも起こりやすい失敗です。

失敗1　同じフォルダ確認を繰り返す Clineが Get-ChildItem などの一覧取得コマンドを、書き方を変えながら何度も提案することがあります。作業フォルダが空だと既に分かっており、新しい情報が得られないなら、回数ではなく目的の重複を理由にRejectし、人間が停止条件を伝えます。
調査を止める指示The workspace is empty, and directory inspection is complete. Do not run any more directory-listing commands. Now show the implementation plan only. Do not create or edit files yet.

日本語で伝える場合は、次を送ります。

調査を止める指示（日本語）作業フォルダは空で、フォルダの確認は完了しています。 これ以上、一覧取得コマンドを実行しないでください。 まだファイルを作成・編集せず、実装計画だけを示してください。
失敗2　1ファイルの依頼を大きなシステムへ変える index.htmlだけと指定しても、Clineが package.json、server.js、Express、React、WebSocket、Pythonサーバなどを含む計画を出すことがあります。もっともらしく詳しい計画でも、依頼に従っているとは限りません。

この場合はActへ進まず、Planモードのまま計画を小さく戻します。
技術構成を直す指示This plan does not follow the requirements. Use only one file: index.html. Put the HTML, CSS, and JavaScript in that file. Store messages only in a JavaScript array. Do not use Python, Node.js, Express, React, Vite, WebSocket, fetch, polling, a database, or external libraries. Keep the revised plan under 10 lines. Do not create or edit files yet. Show the revised plan only.
ここがPlanモードを使う理由です 誤った計画をActモードで実行すると、不要なファイルやパッケージが作られます。Planモードなら、ファイルを変更する前に、人間が逸脱を発見して修正できます。

3.1.7Actを押す前に、承認方法を確認する

次の3.1.8でActを押すと、すぐに実装が始まります。先にこの節を最後まで読み、どの操作を許可し、どの操作を拒否するか確認してください。

3.1.5で Edit files と Execute commands をOFFにしました。そのため、Act開始後はAgentが操作の許可を求めてきます。

判断の基準

ボタン名は操作によって変わります ファイルの作成・編集はSave、コマンドはRun Command、拒否はRejectと表示されます。すべてを機械的に許可せず、何を、どこに対して行う操作なのかを先に確認してください。

3.1.8Actモードへ切り替え、1件ずつ承認する

計画と承認方法を確認したら、入力欄の右下にあるActを1回押します。切り替えた瞬間に、Planモードで作った計画を引き継いで実装が始まります。

Actを押す前が最後の確認です Actへ切り替えた後に、改めて「実装を開始してください」と送る必要はありません。Actを押す操作そのものが、計画を実行させる合図です。

計画に間違いが残っている場合は、Actを押さず、Planモードのまま修正させてください。

画面から目を離さず、Clineが求める操作を1件ずつ確認します。上の表を基準に、必要な操作だけを許可してください。3.5で説明するAgentのループが、そのまま画面に流れます。

対象が index.html だけで、差分が計画どおりならSave
1ファイルでも複数回のSaveが出ることがあります 長いファイルでは、Clineが最初にHTMLとCSSを作り、次にJavaScriptを追記することがあります。回数だけでRejectしません。毎回差分を開き、まだない必要な部分を追加しているならSave、同じ内容の重複や計画外の変更ならRejectします。
見た目が完成していても、ボタンが動くとは限りません JavaScriptの追記をRejectすると、画面はきれいに表示されてもSendが動きません。ブラウザで試して動かなければ、Clineへ次の指示を送り、欠けているJavaScriptだけを追加させます。
画面が表示されたことと、機能が動くことは別
Sendが動かない場合The Send button does not work because the JavaScript is missing. Edit index.html only. Add only the missing JavaScript immediately before </body>. Requirements: - Handle the form submit event - Prevent the default page reload - Validate that user name and message are not empty - Push { name, status, message } into the existing messages array - Display messages below the form - Update the message count - Create DOM elements and use textContent for all user input - Do not use innerHTML - Do not change the existing HTML or CSS - Do not create another file
画面右上の $0.0000 と 6.1k / 128.0k $0.0000 はClineが表示している利用料金です。今回の共有Qwenサーバでは0ドルと表示されます。6.1k / 128.0k は料金ではなく、会話履歴として使っているトークン量です。

会話が長くなるほど応答が遅くなり、古い指示を見失いやすくなります。同じ確認を繰り返し始めたら、人間が止めて次の作業を明示します。

通信が途中で切れたら

通信切断後は、RetryとStart New Taskのどちらかを選ぶ 
terminated: SocketError: other side closed (UND_ERR_SOCKET)

これは作成中のアプリのエラーではありません。ClineとLLMサーバの通信が途中で切れたという意味です。共有サーバの混雑、応答時間の超過、長すぎる出力などで発生します。

状況選ぶもの

どこまでファイルを作ったか分からないStart New Task後、index.htmlだけを確認させる
今回の例ではStart New Task 大きすぎる誤った計画、複数回のフォルダ確認、長い修正履歴が残っている場合、Retryすると同じ履歴を使って再開します。再び切断したり、古い誤案へ戻ったりする可能性があるため、上部の＋またはStart New Taskで新しいタスクを開始します。

追加の2テスト

  1. 名前またはMessageを空にしてSendを押し、投稿されずエラーが出ることを確認する

3.1.11作業ログを読む

いま動かしたばかりのCline画面が、そのまま教材です。作業ログを上までさかのぼって、次の4点を記録してください。

  2. 変更したファイルはどれか。いくつあるか。
  3. Save、Run Command、Rejectをどう判断したか。最低1件について理由を書く。

3.2なぜ同じ依頼でも結果が変わるか

いま演習で、指示の出し方によって結果が変わるのを見たはずです。Agentの失敗は、能力不足だけで起こるわけではありません。必要な情報が渡っていないときにも起こります。

たとえば「ログイン画面を修正して」とだけ頼んでも、Agentには次のことが分かりません。

  • どの画面が対象か
  • 何を変更してよいか
  • 既存の設計ルールは何か
  • 実装後に何を確認すべきか

分からないまま進めば、それらしい何かが出来上がります。PART 1の1.2.3で見た「もっともらしい誤り」が、そのままコードとして現れる形です。

Context Engineeringとは、必要な情報を、必要な時点で渡すことです。Agentが判断できるようにするために行います。

長い説明文を一度に渡すことではありません。

3.2.2渡し方で結果が変わる

次の指示は、作業の目的しか伝えていません。

POORバリデーションを直して。

4種類を揃えると、Agentが判断できるようになります。

BETTERsrc/user.py のメールアドレス検証を修正してください。 APIの戻り値は変更しないでください。 tests/test_user.py の失敗しているテストを通し、既存テストも実行してください。 修正前に、原因と変更予定を簡潔に説明してください。

1行目が対象、2行目が制約、3行目が確認方法、4行目が進め方の指定です。同じ依頼でも、渡し方を変えれば結果が変わります。

情報は多ければよいわけではありません 古い仕様、大量の無関係なファイル、矛盾した指示。どれもAgentの判断を悪くします。PART 1の1.2.1で見たとおり、コンテキストは有限で、真ん中の情報は取りこぼされます。

必要な情報を、必要な範囲で、矛盾なく渡す。これがContext Engineeringの基本です。

3.3どこまで任せるか

Coding Agentが向いているのは、条件が明確で、実行結果を確認できる作業です。

逆は向きません。条件が曖昧で、結果を機械的に確かめられない作業です。

任せやすい作業人間の判断が必要な作業

3.3.1「任せる」の意味

「任せる」は、確認なしで自由に実行させることではありません。

Agentには、最初は狭い範囲だけを任せます。たとえば次のような制約を置きます。

  • このフォルダの中だけを変更してよい
  • テストの実行は許可するが、外部へ送信する操作は許可しない
  • 設定ファイルや認証情報には触れさせない
  • 変更はプルリクエスト経由にし、直接反映はさせない

PART 4以降では、任せられる範囲を安全に広げます。使うのはテスト、Linter、CI、承認手順です。

ただし、範囲を広げる判断そのものは、最後まで人間の仕事です。

自律性は0か1かではなく、段階です。演習0で挙げた3つの仕事が、それぞれどの段階を必要とするかを考えながら読んでください。

3.3.3Agentを使うときの基本手順

いま演習で通った流れを、手順として名前を付けておきます。

Plan　目的、変更範囲、確認方法を整理する。すぐに編集させない。

Act　Agentにファイル探索、実装、テスト実行を任せる。

Review　変更差分、テスト結果、意図しない変更の有無を確認する。

Accept or Reject　変更を採用するか、修正を続けるか、人間が決める。

この4段階は、特定のツールの機能ではありません。基本的な作業手順です。

Clineでも、CLI型のAgentでも同じです。将来まったく別のAgentを使うときも、この4段階は要ります。

Agentの提供形態 Coding Agentには3つの形があります。エディタに統合されるもの（Cline、Cursorなど）。ターミナルから使うもの（Claude Codeなど）。クラウド上で独立して動くもの（Devin、Julesなど）。

見た目と操作方法は違います。しかし3.4のループと、この4段階は共通です。この教材ではClineを使います。

課題 3.1で作成したVibe Chatに、次の機能を追加してください。

各メッセージにDeleteボタンを付けます。ボタンを押すと、そのメッセージだけが消え、Messagesの件数も変わるようにしてください。

編集するファイルは index.html だけです。現在のデザインとSend機能は残してください。

Planを確認するヒント

  • 現在の送信機能とデザインを残しますか。

3.4.2完成条件

次のすべてを満たせば完成です。ブラウザで確認してください。

  1. Ctrl + R を押して、ブラウザを再読み込みします。
  2. メッセージを2件送ります。
  3. 1件目のDeleteを押します。
  4. 1件目だけが消えることを確認します。
  5. 2件目が残ることを確認します。
  6. Messagesの件数が 2 から 1 になることを確認します。
  7. 新しいメッセージを送信できることを確認します。
Deleteが動いても、Sendを壊していたら不合格 Deleteだけを確認してはいけません。Sendも確認してください。Agentは、変更を依頼していない機能を壊すことがあります。

3.4.3うまく動かない場合のヒント

問題があれば、実際に起きたことをClineへ伝えます。例えば、Deleteを押しても消えない、別のメッセージが消える、件数が変わらない、などです。

修正依頼の例I created two messages and clicked Delete on the first message. The first message did not disappear, and the count stayed at 2. Inspect index.html and fix only this problem. Do not redesign the page or add files. After editing, tell me exactly what changed.

差分を確認してSaveします。その後、同じテストをもう一度行います。テスト結果を次の修正に使います。これがAgentの作業ループです。

1　読む　Agentが既存の index.html を読む

2　判断する　メッセージ配列と表示処理の変更箇所を決める

3　提案する　Clineが変更差分とSave / Rejectを表示する

4　実行する　人間がSaveすると、Clineがファイルへ書き込む

5　観察する　人間がブラウザでDeleteとSendを試す

6　修正する　失敗した結果をAgentへ戻し、必要なら2へ戻る

3.5この章で分かったこと

Clineは目標を受け取ります。Clineはファイルを読み、変更を提案します。人間が承認すると、Clineはコードを書きます。人間がコードをコピーして貼り付ける必要はありません。

今回のアプリは練習用です。ページを再読み込みすると、データは消えます。複数の利用者はデータを共有できません。自動テストもありません。アプリが動くことと、実際の仕事で使えることは同じではありません。
