B.1この付録の位置づけ

本教材のPART 5〜6は、もともとNode.jsとTypeScriptで書かれた開発の記録でした。本編をPythonに移したのは、次の2つの理由によります。

  • 読めないコードはレビューできない。PART 2で「出力をまったく読めないなら、正しい答えと自信満々の誤答を区別できない」と書きました。TypeScriptとReactが初見の読者にとって、この前提は成立しません。
  • 言語が混ざるほどローカルモデルの失敗が増える。フロントとバックで言語が違うと、モデルは常に切り替えを強いられます。単一言語のほうが破綻しにくくなります。

とはいえ、既存のTypeScriptプロジェクトに導入する場合や、フロントエンドにReactが必要な場合は、原構成のほうが実態に合います。章の骨格、プロンプトの出し方、イテレーションの切り方、/selfcheck.md の使い方は、どちらの構成でも共通です。

B.3PART 5相当：モノレポ環境の強化

構成は frontend/（React, Vite, Tailwind CSS, Playwright）、backend/（Hono）、aws/（AWS CDK, cdk-nag）の3パッケージです。

PROMPT（/deep-planning）npm workspacesのセキュリティを強化したい。 - 以下のフォルダ構成を確認し、セキュリティで不足する点の改善プランを出す。 - frontend/ (React, Vite, Tailwind CSS, Playwright) - backend/ (Hono) - aws/ (AWS CDK, cdk-nag) - 以下の基本的な技術スタックを追加し、開発環境を強化する - GitHub Actions - actionlint / zizmor - Renovate (minimumReleaseAgeを必須とする) - Husky + lint-staged - gitleaks

プランを実行すると、Renovate、gitleaks、Husky、lint-stagedの設定ファイルが作成され、既存のGitHub Actionsワークフローも更新されます。完了後は /selfcheck.md で検証します。原構成で実際に必要になった修正は次のとおりでした。

  • CI/CDに脆弱性チェックのコマンドが漏れていた
  • huskyの古い文法によるWarning出力
  • npm audit が報告した脆弱性の解決
  • 各種CLIツールのDev Containerでのセットアップ追加

確認観点は本編5.3.3と同じです。ローカルとCIで同じコマンド体系になっているか（npm scripts に統一されているか）、Lint / Format / Test / Typecheck がCIで実行されているか、失敗時にどのコマンドが落ちたかログで追えるか。

B.4PART 5相当：実装

B.4.1共通部分（shared）

原構成の shared/ は、TypeScriptの型定義とZodスキーマをフロントとバックで共有するためのものでした。両側が同じ言語だから成立した構成です。本編のPython版では、この役割をPydanticモデルが単独で担い、フロント側へはOpenAPIスキーマ経由で渡すという形に組み替えています。

実装後は /selfcheck.md で品質を確認します。原構成では、型定義とZodスキーマの一式について、テスト品質とコード品質の両面で高い評価が得られました。

B.4.2バックエンド（Hono）

Honoは軽量かつ高速なWebフレームワークで、Cloudflare WorkersやAWS Lambdaへのホスティングが容易です。ミドルウェアによりOpenAPI規格との連携もしやすくなっています。

実装前に、Honoの公式サイトが公開している llms.txt をローカルに置いてエージェントに参照させます。

mkdir -p docs/ref/hono
curl -o docs/ref/hono/llms.txt https://hono.dev/llms.txt
PROMPT@/docs/design/implementation_plan_vibe_order.md と @/packages/backend/docs/design.md を元に、backend/部分の実装計画を検討してください。各イテレーションで細かく品質確認をしながら着実に進めるプランを取ってください。honoの扱い方が分からない部分は @/docs/ref/hono/llms.txt を参照してください。

原構成では、エージェントが最初に出した計画を「10点満点中何点か」と問うたところ7.5点と自己評価し、WebSocket統合の再検討などの改善点を提示しました。それを踏まえて詰め直し、9イテレーションからなる計画が確定しています。

実装中、コンテキスト使用率が約70%に達した時点で、残りのイテレーションを /docs/prompt/backend_continuation_iterations5-9.md としてドキュメント化し、新しいセッションへ引き継ぎました。この引き継ぎの作法は本編と共通です。

B.4.3フロントエンド（React + Vite）

ViteにもHono同様に llms.txt があります。

mkdir -p docs/ref/vite
curl -o docs/ref/vite/llms.txt https://vite.dev/llms.txt

原構成では10回のイテレーションに分ける計画が提案され、Phase単位でセッションを切り替えながら進めました。最終的に173個のテストがすべてパスしています。実装中に .clineignore が .env の作成を防いでいることも確認できました。

SPA構成でのコンテキスト消費 React + Vite + Tailwindの構成は、1つの画面を作るのに複数のファイルを同時に触ります。クラウドの大型モデルなら問題になりませんが、ローカルの27Bクラスではコンテキストを急速に消費し、差分編集の失敗も増えます。本編がサーバ側HTMLを採用したのはこのためです。原構成で進める場合は、セッションの切り替え回数が増えることを見込んでください。

B.5PART 6相当：リリース

AWS CDKをTypeScriptで書き、cdk-nagでルールチェックを行います。デプロイ前の確認は cdk synth、CI/CDはGitHub Actionsです。

PROMPTnpm run test -w @myapp/aws を実行してください。deprecatedが発生する箇所については、MCPで調べてください。

E2EテストはPlaywrightのJavaScript版を使います。テストの内容も、失敗時にターミナルのログをそのまま渡してデバッグさせる進め方も、本編7.5と同じです。

MCPについては本編7.3の説明がそのまま当てはまります。MCPはモデルとも言語とも独立した層なので、原構成でも本編でも扱いは変わりません。
