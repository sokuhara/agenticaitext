A.1この付録の位置づけ

本教材のハンズオンは、モデルを手元で動かす前提で書かれています。クラウドAPIを使う構成（Amazon BedrockのClaudeなど）でも同じ手順で実装できますが、有料であり、アカウントとモデルアクセスの申請が必要になります。授業や研究室でまとめて環境を配る場合は、課金経路の用意そのものが壁になります。そこで本教材はローカルを既定にしています。

実際に変わるのはモデルとプロバイダの部分だけです。エージェントはCline、リポジトリ構成もプロンプトもコマンドも共通です。PART 1で見た「モデルとプロバイダは別の層である」という整理が、そのまま効いてきます。

ローカルとクラウドで変わるもの／変わらないもの 変わる：API Provider、モデル名、費用の考え方（自前の計算資源 ↔ 従量課金）、1セッションで任せられる作業量
変わらない：Cline、モノレポ構成、.clinerules、/deep-planning や /selfcheck.md といったコマンド、CIの組み方

A.2前提環境と2モデル構成

1つのモデルで全部やろうとすると、軽い作業に大きなモデルを占有してしまい、逆に軽いモデルで長い実装ループを回すと途中で壊れます。用途で2つに分けるのが扱いやすい構成です。

役割モデルOllamaタグ置き場所
エージェント本体
（実装・計画・selfcheck）		 Qwen3.8 27B qwen3.8:27b 研究室の共有サーバ（A.3.4）
PART 2の演習1
軽作業・要約・下書き		 Qwen3.5 4B qwen3.5:4b 各自のノートPC
▲用途で分ける2モデル構成

Qwen3.8 27Bは、Ollamaライブラリのデフォルトビルドが約18GBのQ4_K_M量子化で、tool calling（ツール呼び出し）とthinkingに対応しています。Coding Agentが必要とするのはまさにこのtool callingなので、ここが対応しているかどうかがモデル選びの分かれ目になります。24GB程度のVRAMがあれば、実用的なコンテキスト長で載ります。

Qwen3.5 4Bも同様にツール呼び出しに対応しています。PART 2の演習1のように、対象が明確で1回の変更が小さい作業には十分です。ただしPART 6のような長い実装イテレーションを任せるには小さすぎます。4Bは小さく正確な依頼までと割り切り、PART 5以降は27Bで進めてください。

確認しておくこと Ollamaのモデルライブラリはタグの構成が頻繁に変わります。実際に使う前に ollama list と公式ライブラリページで、タグ名と量子化、対応機能（tools / thinking）を確認してください。本教材の記載は執筆時点のものです。

A.3Ollamaのセットアップ

A.3.1バージョンの確認とモデルの取得

本付録ではOllama 0.32.15を前提とします。Ollama自体の入れ方（Windows / macOS / Linux）は、PART 2の2.3.1にあります。ここでは入っている前提で進めます。

まずバージョンを確認し、2つのモデルを取得します。

ollama --version
# ollama version is 0.32.15

# エージェント本体（約18GB）
ollama pull qwen3.8:27b

# 軽作業用（各自のPC）
ollama pull qwen3.5:4b

# GPUが認識されているか
nvidia-smi
ollama ps

A.3.2コンテキスト長を明示的に伸ばす

ここが一番の落とし穴です。Ollamaのデフォルトのコンテキスト長は、Coding Agentの用途には短すぎます。気づかないうちに会話履歴が切り詰められ、エージェントが「さっき作ったファイル」を忘れて破綻します。モデル自体が長いコンテキストに対応していても、num_ctx を明示しなければ意味がありません。

Modelfileで、用途に合わせた設定を焼いた派生モデルを作っておくのが確実です。PART 7で自作Agentを動かすときも、この設定が効きます。コード側で num_ctx を指定して回るのは1回の呼び出しだけで、モデル側の既定を変えておくほうが確実です。

# Modelfile.agent
FROM qwen3.8:27b
PARAMETER num_ctx 131072
ollama create qwen38-agent -f Modelfile.agent
ollama show qwen38-agent   # num_ctx が反映されているか確認

コンテキストを伸ばすとKVキャッシュがVRAMを食います。ollama ps で CPU への退避が起きていたら、num_ctx を下げるか、KVキャッシュの量子化を検討してください。CPUに落ちた瞬間に、体感速度は実用外まで落ちます。

A.3.3サーバとして公開する（研究室・教室で共有する場合）

各自のPCに27Bを配るより、GPUのある1台に立てて共有するほうが管理も配布も楽です。

# サーバ側（LANに公開）

# クライアント側から疎通確認

A.3.4共有サーバへ接続する（Cloudflare Access経由）

研究室のサーバを学外からも使う場合、認証を前に置きます。ここではCloudflare Accessで保護した例を示します。

OllamaはOpenAI互換のエンドポイントを持っています。/v1 を付けるだけです。既存のクライアントがそのまま使えます。

接続先使うモデル
各自のPChttp://localhost:11434qwen3.5:4b
研究室のサーバhttps://<サーバのホスト名>/v1qwen3.8:27b
27Bは各自のPCには入っていません 手元にあるのは qwen3.5:4b だけです。PART 3以降で使う qwen3.8:27b は、サーバ側にあります。

ollama list を手元で打っても27Bは出てきません。それが正常です。18GBを全員が落とすと回線も容量も持ちません。

まず疎通を確認する

import os

from openai import OpenAI

client = OpenAI(
    base_url="https://<サーバのホスト名>/v1",
    api_key="ollama",                       # Ollamaは鍵を見ない。何でもよい
    default_headers={
        "CF-Access-Client-Id": os.environ["CF_ACCESS_CLIENT_ID"],
        "CF-Access-Client-Secret": os.environ["CF_ACCESS_CLIENT_SECRET"],
    },
)

for m in client.models.list().data:
    print(m.id)

一覧に qwen3.8:27b が出れば接続できています。

認証情報をコードに書かないこと サービストークンをソースへ直接書くと、そのままGitに入ります。PART 5の5.5で扱う話が、ここで先に出てきます。

環境変数に置いてください。.env を使う場合は、.gitignore に入っていることを必ず確認します。

うっかりコミットしたら、削除では済みません。Cloudflareのダッシュボードでトークンを失効させ、作り直してください。履歴からの削除より、失効のほうが確実です。 
# PowerShell（その場限り）
$env:CF_ACCESS_CLIENT_ID="<発行されたID>"
$env:CF_ACCESS_CLIENT_SECRET="<発行されたSecret>"

# macOS / Linux

Cline / Continue から使う

プロバイダは OpenAI Compatible を選びます。Ollamaプロバイダではありません。

設定項目値
ProviderOpenAI Compatible

Continueの場合は、設定ファイルに書きます。

models:
  - name: Lab 27B
    provider: openai
    model: qwen3.8:27b
    apiBase: https://<サーバのホスト名>/v1
    apiKey: ollama
    roles: [chat]
    requestOptions:
      headers:
        CF-Access-Client-Id: ${{ secrets.CF_ACCESS_CLIENT_ID }}
        CF-Access-Client-Secret: ${{ secrets.CF_ACCESS_CLIENT_SECRET }}
この値はOSの環境変数からは読まれません ${{ secrets.X }} と書いても、VS Codeの拡張機能は export したOS環境変数を見ません。.env ファイルに書く必要があります。

探しに行く順序は次のとおりです。
順場所使いどころ
1作業フォルダの .envそのプロジェクトだけで使う
2作業フォルダの .continue/.env同上。Continue専用にしたいとき
3~/.continue/.env全プロジェクト共通。授業ではこれが楽です
4OSの環境変数Continue CLI のみ。VS Code拡張では効きません

授業では3番を勧めます。1か所書けば、どのフォルダを開いても効きます。

# ~/.continue/.env
CF_ACCESS_CLIENT_ID=<発行されたID>
CF_ACCESS_CLIENT_SECRET=<発行されたSecret>

値を引用符で囲まないでください。dotenv形式です。

Windowsでの作り方

~ は C:\Users\<ユーザー名> です。作るのは C:\Users\<ユーザー名>\.continue\.env になります。

エクスプローラーとメモ帳では作れません 理由が2つあります。

1. 拡張子が隠れている。メモ帳で保存すると .env.txt になります。見た目は .env なので、間違いに気づけません。

2. 先頭がドットのファイルを作りにくい。エクスプローラーの「新規作成」では名前を受け付けないことがあります。

PowerShellで作ってください。 
# 1. 自分のホームがどこか確認する
echo $HOME

# 2. フォルダを作る（すでにあれば何も起きない）
New-Item -ItemType Directory -Force -Path "$HOME\.continue" | Out-Null

# 3. 中身を書く
[System.IO.File]::WriteAllText(
  "$HOME\.continue\.env",
  "CF_ACCESS_CLIENT_ID=<発行されたID>`nCF_ACCESS_CLIENT_SECRET=<発行されたSecret>`n"
)

# 4. 確認する
Get-Content "$HOME\.continue\.env"
Set-Content を使わない理由 Set-Content -Encoding utf8 は、PowerShell 5.1 だとファイルの先頭にBOMという見えない印を付けます。その結果、1行目のキー名が ﻿CF_ACCESS_CLIENT_ID のように読まれ、値が見つかりません。

画面上は正しく見えるので、原因にたどり着くのに時間がかかります。上の WriteAllText はBOMを付けません。

VS Codeで作る場合

コマンドが苦手なら、こちらでも作れます。

  1. PowerShellで New-Item -ItemType Directory -Force -Path "$HOME\.continue" を実行してフォルダだけ作る
  2. VS Codeで File → Open Folder、アドレス欄に %USERPROFILE%\.continue と入力して開く
  3. 新規ファイルを作り、名前を .env にする
  4. 2行書いて保存する

VS Codeなら拡張子が勝手に付きません。右下のエンコーディング表示が UTF-8 であることも確認できます。

仮想環境でWindowsを使っている場合 Parallels などでmacOS上のWindowsを動かしていると、C:\Mac\Home のようにMac側のフォルダが見えていることがあります。そこはWindowsのホームではありません。

必ず echo $HOME で確認してから作ってください。

macOS / Linux の場合

mkdir -p ~/.continue
cat > ~/.continue/.env <<'EOF'
CF_ACCESS_CLIENT_ID=<発行されたID>
CF_ACCESS_CLIENT_SECRET=<発行されたSecret>
EOF
cat ~/.continue/.env

書いたら、VS Codeを再読み込みしてください。（Ctrl + Shift + P → Reload Window）読み込みは起動時に行われるので、開いたままだと反映されません。

作業フォルダに置く場合 1番か2番を選んだときは、.gitignore に .env が入っていることを必ず確認してください。PART 5のテンプレートには最初から入っています。

3番（~/.continue/.env）なら、リポジトリの外にあるのでコミットの心配はありません。授業で勧める理由のひとつです。
カスタムヘッダに対応していない場合 拡張機能のバージョンによっては、ヘッダを追加する欄がないことがあります。その場合の逃げ道は2つです。

1. トンネルを掘る。cloudflared access tcp でローカルのポートへ転送し、Base URLを http://localhost:<ポート>/v1 にします。認証はトンネル側が処理するので、拡張機能はヘッダを知らずに済みます。

2. 手元にプロキシを立てる。ヘッダを足して転送するだけの小さなサーバを書きます。PART 7を終えていれば、数十行で書けます。
共有サーバは同時に使われます 1台のGPUを全員で使うので、誰かが長い作業を回していると、応答が遅くなります。これは故障ではありません。

待ち時間が長いときは qwen3.5:4b を手元で使ってください。PART 1と2の演習は、それで足ります。

サーバ側で ollama ps を見れば、いま何が載っているか分かります。

A.6ローカルで詰まるところ

A.6.1コンテキストが静かに切れる

症状としては、エージェントが直前に作ったファイルを忘れる、同じ修正を何度も提案する、計画の途中から辻褄が合わなくなる、といった形で出ます。エラーが出ないので気づきにくいのが厄介です。A.3.2の num_ctx 設定を最初に済ませておいてください。

A.6.2差分編集の失敗

Clineのファイル書き換えは、置換対象の文字列が厳密に一致することを要求します。ローカルモデルはここでリトライが増えがちです。対策は、1回の依頼で触るファイル数と変更量を小さくすること。PART 6の「イテレーションを細かく切る」という方針を、より細かく適用してください。

A.6.3ツール呼び出しが本文として出力される

ツール呼び出しを実行せず、呼び出しの内容をそのままテキストとして書き出してしまうことがあります。この種の不具合はランタイム側の更新で直ることが多いので、同じ症状が続く場合はOllamaのバージョンとモデルタグの組み合わせを変えて試してください。

A.6.4自動承認を長く回さない

PART 3の演習ではAuto-approveを設定して一気に走らせましたが、ローカルモデルでこれをやると、壊れた状態のまま長時間進んでしまいます。承認を挟む回数を増やすほうが、結果的に速く終わります。PART 5で整えるブランチ保護とCIが、ここでの最後の砦になります。

A.7.2プロプライエタリとオープンウェイト

2026年のモデル選びで最初に来る分岐は、性能でも価格でもなく「重み（weights）が公開されているかどうか」です。

A.7.4規模、MoE、量子化

ローカルで動かすとき、性能スコアより先に効いてくる要素です。

  • パラメータ数。モデル名末尾の 4b、27b がこれです。大きいほど賢く、大きいほどメモリを食い、大きいほど遅くなります。
  • dense と MoE。denseは全パラメータを毎回使います。MoE（Mixture of Experts）は内部を多数の専門家に分け、入力ごとに一部だけを動かします。「総1.6兆／アクティブ49億」という表記は、置いておくメモリは総パラメータ分必要だが、計算は一部だけ、という意味です。1枚のGPUで動かしたいなら、denseの中型モデルのほうが現実的です。
  • 量子化。重みを4bitや8bitに落として容量を削ります。Q4_K_M のような表記がそれです。品質はわずかに落ちますが、容量はおおよそ4分の1になります。
規模4bit量子化での目安動く環境向いている作業
3B〜8B2〜6GBノートPC（GPUなしでも可）要約、整形、小さく正確な依頼
14B〜32B8〜20GBGPU 1枚（24GBクラス）エージェントとしての実務。本教材の中心
70B以上・大型MoE40GB〜数百GB複数GPU、サーバ研究室・組織で共有

A.7.6データの取り扱い

クラウド経由のマネージドサービスでは「送信データは学習に利用しない」と規約に明記されているのが一般的です。ホスティングプラットフォームでは、学習可否やログ保持が下流プロバイダや設定によって異なります。機密性の高いコードを扱う際は、学習フラグの有無だけでなく、保持期間やZero Data Retentionの可否まで確認してください。

「ローカルなら外に出ない」は条件付きです モデルを手元で動かすこと自体は、外部送信を伴いません。ただしネットワークを使う機能を足せば、そこから出ていきます。ウェブ検索、外部APIを叩くMCPサーバ、クラウド同期のかかったフォルダ、テレメトリ。構成全体で確認してください。手元で動かすことは前提条件であって、それだけで完結する保証ではありません。

A.8Dev Containerで環境を揃える

授業や研究室でPCの状態がまちまちなとき、Dev Containerを使うと同じ環境を再現できます。PART 5の必修ではありませんが、「私の環境では動きません」の対応に時間を取られるくらいなら、最初に配ってしまうほうが早い場面はあります。

Agentにコマンド実行を任せる以上、ローカルマシンそのものを作業場にしないという意味もあります。壊れても捨てて作り直せます。

// .devcontainer/devcontainer.json
{
  "name": "vibe-order",
  "image": "mcr.microsoft.com/devcontainers/python:3.12",
  "features": {
    "ghcr.io/va-h/devcontainers-features/uv:1": {},
    "ghcr.io/devcontainers/features/node:1": {}
  },
  "postCreateCommand": "uv sync",
  "customizations": {
    "vscode": { "extensions": ["saoudrizwan.claude-dev", "charliermarsh.ruff"] }
  }
}
インストーラをpostCreateCommandに書かないこと curl -LsSf https://astral.sh/uv/install.sh | sh && uv sync のような書き方をよく見かけますが、インストール直後の uv がそのコマンド内のPATHで解決される保証はありません。同じシェルの中で続けて呼ぶと失敗することがあります。

Featureとして入れるか、uvが同梱されたイメージを使ってください。postCreateCommand には uv sync のような、すでにPATHにあるものだけを書きます。

Node.jsのFeatureを入れているのは、MCPサーバの多くがnpx経由で配布されているためです。アプリケーション側でJavaScriptを書くわけではありません（PART 7）。

GitHub Codespacesを使う場合も、同じ devcontainer.json がそのまま効きます。手元にDockerがない受講者がいるなら、そちらのほうが確実です。

A.9補完が出ない・二重に出るとき

セットアップの06でContinueのタブ補完を入れた場合の話です。補完が出ないという相談の原因は、ほとんどが他の補完機能との干渉です。

A.9.1まず、どちらの症状か切り分ける

症状原因
灰色の候補がまったく出ない他の拡張機能が先に応答している。またはContinue側が無効
候補が出るが、明らかに速い／英語のコメントばかりそれはCopilotの候補です。Continueではありません
候補がちらつく、二重に見える2つの補完が同時に動いています

2番目が厄介です。動いていると思っていたものが、実は別の拡張機能だったという状態になります。ローカルで動かしているつもりが、クラウドに送っていることになります。

A.9.2GitHub Copilotを切る

3段階あります。下へ行くほど強く切れます。

1. インライン補完だけ止める

画面右下のステータスバーにあるCopilotのアイコンをクリックし、Disable Completions を選びます。チャット機能は残ります。

設定から行う場合は、Ctrl（macOSは Cmd）+ , で設定を開き、検索欄に次を入れます。

github.copilot.enable

Edit in settings.json を開いて、次のように書きます。

"github.copilot.enable": {
  "*": false
}

2. このプロジェクトでだけ無効にする

拡張機能のパネル（Ctrl + Shift + X）でGitHub Copilotを探し、歯車から Disable (Workspace) を選びます。

授業ではこれを勧めます。他のプロジェクトでは今までどおりCopilotが使えて、この教材のフォルダでだけ切れます。

3. 完全に無効にする

同じ歯車から Disable を選びます。VS Codeの再読み込みを求められたら従ってください。

Copilot以外にも補完を出す拡張機能があります Tabnine、Codeium、Amazon Qなど、入れた覚えがなくても学校や会社の初期設定で入っていることがあります。
拡張機能パネルの検索欄を空にして一覧を上から見てください。「completion」「AI」「assistant」を名前に含むものが該当します。

A.9.3Continue側を確認する

他を切っても出ない場合は、Continue自体が止まっている可能性があります。

  • 画面右下のステータスバーにあるContinueの表示をクリックし、Enable Tab Autocomplete が有効か確認する
  • 設定に書いたモデル名が、ollama list の表示と1文字も違わないか確認する（qwen2.5-coder:1.5b のタグまで含めて）
  • roles に autocomplete が入っているか確認する。チャット用の設定だけでは補完は動きません
  • ターミナルで ollama ps を実行し、補完用モデルが載るか見る。何も載らないなら、Continueから呼べていません

A.9.4それでも分からないとき

VS Codeのログを見ます。Ctrl（macOSは Cmd）+ Shift + P でコマンドパレットを開き、Toggle Developer Tools を実行して Console タブを見てください。

モデル名の誤りや接続エラーは、ここに出ます。出ているエラーをそのままAgentに貼れば、原因の見当は付きます。PART 2で身につけた方法が、そのまま使えます。

A.10Continueを使えない場合：ターミナルから渡す

PART 2の演習1は、ContinueでAIにファイルを渡す前提で書いてあります。Continueを入れられない場合は、ターミナルから同じことができます。

ただし、本編では扱いません。操作の経路が2つあると、どちらを使うべきか迷うからです。

A.10.1ファイルを渡す

ollama run に長い文章を貼ると、途中で改行が実行されることがあります。貼り付けず、ファイルをそのまま渡してください。

# PowerShell
Get-Content controls.txt | ollama run qwen3.5:4b

# macOS / Linux
cat controls.txt | ollama run qwen3.5:4b

この方法だと1行で済み、貼り付け事故も起きません。

A.10.2指示を一緒に渡す

ファイルだけ渡しても、何をしてほしいか伝わりません。指示を先に書いたファイルを作ります。

# PowerShell
"Fill in the blank. Output one line only.`n" +
"#sign-kushikatsu .board { fill: ______; }`n" +
"Replace ______ with a hex color for saffron orange." |
  ollama run qwen3.5:4b

穴埋めの形にする理由は、PART 2の2.3.5と同じです。4Bに考えさせる場所は、1回に1か所だけにします。

A.10.3返ってきたものの扱い

ここから先はContinueの場合と変わりません。返ってきたCSSを shinsekai_remix.html のA区間へ貼り、保存して再読み込みします。

できれば Continue を使ってください ターミナルでも進められますが、ファイルを開いたまま渡せるContinueのほうが確実です。貼り付けの事故が起きず、返答のコピーもボタン1つで済みます。

導入手順はセットアップの06にあります。

A.11共有サーバにつながらないときの切り分け

Clineが動かないとき、原因はサーバ側かCline側のどちらかです。ターミナルから直接叩けば、どちらかが分かります。

PowerShellで実行します。すべて1行で打ってください。折り返すと、後半が別のコマンドとして実行されます。

curl ではなく curl.exe PowerShellの curl は別のコマンドの別名です。必ず curl.exe と書いてください。-H の書き方が違って失敗します。

A.11.1段階1：認証とモデル一覧

curl.exe "https://<サーバ>/api/tags" -H "CF-Access-Client-Id:<ID>" -H "CF-Access-Client-Secret:<Secret>"
返ってきたもの意味
JSON（{"models":[...]}）認証は通っている。段階2へ
302 Found のHTML認証情報が届いていない。ヘッダの綴りと値を確認
何も返らないURLの綴り、またはサーバが落ちている

JSONが返ったら、その中の name がモデル名です。ClineのModel IDと一致しているか確認してください。

capabilities は当てになりません /api/tags の capabilities には completion しか出ないことがあります。ツール対応の有無は、これでは判断できません。

正確に見るには /api/show を使います。そちらには tools が含まれます。

A.11.2段階2：Clineと同じ経路で叩く

Clineが使うのは /v1/chat/completions です。同じ形で投げます。

'{"model":"<モデル名>","messages":[{"role":"user","content":"hi"}],"stream":true}' | Set-Content -Path t.json -Encoding ascii
curl.exe -s -N "https://<サーバ>/v1/chat/completions" -H "CF-Access-Client-Id:<ID>" -H "CF-Access-Client-Secret:<Secret>" -H "Content-Type: application/json" -d "@t.json"
返ってきたもの意味
data: {...} が並び、最後に data: [DONE]サーバは完全に正常。原因はCline側の設定です
途中で切れるサーバ側かネットワーク。講師に知らせる
404URLに /v1 が入っていない
段階2が通ったら、Clineの設定です 見るのはこの3つです。

1. Base URL の末尾が /v1 か。いちばん多い失敗です
2. Custom Headers の名前が壊れていないか。heaCF-Access-... のようになっていないか
3. Model ID が段階1で見た名前と一致しているか

A.11.3ファイルに書くときの注意

JSONを Set-Content でファイルにするとき、-Encoding ascii を付けてください。付けないとBOMが入り、サーバがJSONとして読めません。

URLは必ず " で囲みます。囲まないと https: のコロンをPowerShellが誤解釈します。
