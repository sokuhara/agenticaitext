C.1本章の概要

本編から引き継ぐこと ここから先で何を選んでも、次の5つは変わりません。

1. make check を通してから次へ進める（PART 5）
2. E2Eテストは単体テストとは別に必要（C.5）
3. デプロイ用の権限は、開発者本人の強い権限と分ける（C.2）
4. シークレットをリポジトリへ置かない（PART 5の5.5）
5. ログ、コスト、停止手順が運用には要る（C.6）

ここでは、作ったアプリケーションを実際の環境へ出し、動作確認と公開判断を行う一連のプロセスを扱います。

C.1.1共通するのは流れだけです

どこへ出すにしても、順序は同じです。

ビルド → 検証 → デプロイ → E2E確認 → リリース判断

ただし、共通するのはこの流れだけです。成果物の形、認証、ネットワーク、データの保存先、監視、そして失敗したときの戻し方は、デプロイ先ごとにかなり違います。「どこでも同じ」と考えて進めると、必ずどこかで詰まります。

C.1.2標準ルートを1つ決めます

ルート必要なもの
標準Docker ComposeDockerのみ。課金もクラウドアカウントも不要
発展AWS（CDK for Python）AWSアカウント、OIDC設定、ロール設計
発展PaaS各サービスのアカウント

授業や研究室で進めるなら、Docker Composeを標準にしてください。学生が手元で動かして確認でき、FastAPIの実行形態がそのまま見え、E2Eまで一貫して進められます。Agentに書かせたDockerfileやcompose.yamlをレビューする題材にもなります。

AWSを本編に入れない理由 AWSで公開すると、学生が時間を使うのはPythonでもAgentic Codingでもなく、IAMの権限設定になります。それ自体は重要な技術ですが、この教材の目的ではありません。AWSルートはC.4.2以降を参照してください。
コンテナは何のための道具か Dockerは配布と実行環境を揃えるための選択肢であって、Agentic AIに必須の技術ではありません。手元でFastAPIを動かすだけなら uv run uvicorn で足ります。

Dev Containerも同じで、再現可能な開発環境を作る道具です。Agentを安全に閉じ込める箱ではありません。Dockerソケットやホストの広いディレクトリをマウントしていれば、コンテナの外へ手が届きます。権限制御はコンテナではなく、渡す権限そのもので行ってください。

C.2デプロイ環境の準備

C.2.1デプロイ用の権限を分ける

AWSを使う場合は、Agentic Codingでインフラを操作・構築するために、事前に必要なCLIの設定や権限付与を行っておきます。エージェントに強い権限を渡すことになるので、PART 4の4.4.3で決めた「守る対象」を、ここで実際に適用してください。

エージェントに渡す権限 デプロイ用の認証情報は、開発者自身のものではなく専用のものを用意します。エージェントは指示を取り違えます。取り違えたときに何が消えるかは、渡した権限の範囲で決まります。

C.3デプロイ環境の実装

ここからはMCP（Model Context Protocol）でエージェントに外部の情報源を繋ぎます。

外部ツールをAgentへ接続する場合 MCPは、Agentにブラウザ、ドキュメント、データベースなどを接続するための方法のひとつです。デプロイの技術ではありません。必要なものだけを有効にし、信頼できるサーバだけを使ってください。詳しくはPART 7の7.5にあります。

C.3.1実装計画の策定

まず、設計書を参照させながら実装計画を立ててもらいます。

PROMPT@/docs/design/implementation_plan_vibe_order.md と @/docs/design/deploy.md を元に、デプロイ構成の実装計画を検討してください。

標準ルート（Docker Compose）では、この位置に Dockerfile と compose.yaml が来ます。Agentに書かせて構いませんが、生成された設定ファイルは必ず自分で読んでください。ヘルスチェック、公開ポート、環境変数の渡し方、ボリュームの範囲。ここを読まずに通すと、意図せず広い範囲を外へ出すことがあります。

# compose.yaml（骨格）
services:
  app:
    build: .
    ports: ["8000:8000"]
    environment:
      - APP_ENV=staging
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8000/api/health"]
      interval: 10s
      retries: 5
発展：AWS Lambdaへ出す場合 FastAPIはASGIアプリなので、CDKで関数を数行定義するだけでは動きません。Mangumのようなアダプタを挟むか、Lambda Web Adapterを使うか、コンテナイメージとして配布する必要があります。依存パッケージも、LambdaのLinux環境に合う形で同梱しなければなりません。

Python 3.12自体はLambdaで利用できますが、「CDKを数行書けば出る」わけではありません。授業で扱うなら、ここだけで1コマ分の重さがあると考えてください。

Docker Composeで進める場合は、compose.yaml とアプリケーション用の Dockerfile がこの位置に来ます。

C.3.2デプロイ前の動作確認

実装が完了したら、デプロイ前に定義が正しく解決できるかを確認します。

uv run cdk synth          # CloudFormationテンプレートの生成を確認
# または
docker compose config     # composeファイルの構文と変数展開を確認
docker compose up --build # ローカルで一度立ち上げる

C.4デプロイ

ここからは、実際にデプロイするためのCI/CDシステムを構築し、GitHub Actionsを通じてデプロイを実行していきます。PART 5で作ったCIワークフローに、デプロイのジョブを足す形になります。

C.4.1CI/CD環境の設計

検証（PART 5で作った check ジョブ）とデプロイを分け、検証が通ったものだけがデプロイへ進むようにします。デプロイは自動ではなく手動起動にしておくと、事故の範囲を限定できます。

C.4.2CI/CD環境の実装

Actモードへ移行したエージェントは、計画に従って段階的にパイプラインを実装します。

# .github/workflows/deploy-staging.yml
name: Deploy staging

on:
  workflow_dispatch:

permissions:
  contents: read
  id-token: write

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: staging

    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-python@v6
        with:
          python-version: "3.12"
      - uses: astral-sh/setup-uv@v6
      - run: uv sync --locked
      - run: make check
      - uses: aws-actions/configure-aws-credentials@<固定したコミットSHA>
        with:
          role-to-assume: ${{ vars.AWS_DEPLOY_ROLE_ARN }}
          aws-region: ap-northeast-1
      - run: uv run cdk diff
      - run: uv run cdk deploy --require-approval never
permissions だけでは認証できません id-token: write はOIDCトークンを発行する許可にすぎません。AWS側に作った限定ロールを引き受ける処理（configure-aws-credentials）がないと、デプロイは通りません。GitHub ActionsのOIDCは、長期のAWSキーをSecretsに置かず、実行ごとの短期資格情報を使うための仕組みです。ロール側の信頼ポリシーで、リポジトリとブランチを絞ってください。

認証情報を直接置かず、OIDCによる一時的な権限で動かします。PART 5の5.5で入れたgitleaksは、うっかりコミットされた鍵を止めるための最後の網ですが、そもそも鍵を置かない設計のほうが先です。

C.4.3CI/CD環境の検証

設計・実装が完了したら、エージェントに検証を依頼します。ワークフローそのものの検査にはactionlintとzizmorを使います。

C.4.4プルリクエストとCIチェック

GitHubにプルリクエストを作成し、自動テスト（CIチェック）を実行します。

CIが落ちるとマージできない。これがブランチ保護の効果です

非推奨（deprecated）APIの警告やテストエラーが発生した場合は、7.3で接続したMCPサーバを活用して、エージェントに原因特定と修正を依頼します。

PROMPTmake check を実行してください。DeprecationWarning が出る箇所については、MCPで現在の推奨される書き方を調べてから修正してください。

C.4.5デプロイの実行

チェックが通った後、GitHub Actionsの「Run workflow」からデプロイを実行します。

make check で止まると、以降のデプロイ手順は実行されない

途中でエラーが発生した場合は、エラーログをそのまま解析させ、修正と再実行を繰り返して正常完了を目指します。依存関係の解決やパスの設定不足が原因であることが多く、ログを渡せばエージェントが特定できます。

C.5デプロイ後の動作確認

C.5.1E2Eテストの実装

実際の環境で正しく機能するか確認するため、Playwrightを用いたE2E（End-to-End）テストを構築します。PlaywrightにはPython版があり、pytestプラグインが用意されています。

本番に出してからE2Eを走らせない 流れはこうします。ローカル → CI → Stagingへデプロイ → StagingでE2E → 人間の承認 → Production。本番で初めてE2Eを回す構造にすると、失敗が利用者に見えてしまいます。

E2Eを書くときは、次を守ってください。

  • BASE_URL を環境変数で切り替える。テストコードにURLを埋め込まない
  • テスト用のデータを、テストの中で作成し、終わったら削除する
  • 失敗時にスクリーンショットとtraceを保存する
  • 本番データや実ユーザーのアカウントを使わない
  • サインインが必要なら、テスト専用アカウントと権限を用意する
uv add --dev pytest-playwright
uv run playwright install chromium
PROMPT/deep-planning <デプロイしたフロントエンドのURL> についてサインインが成功しました。サインイン後の画面のE2Eテストを実装する計画を立ててください。
# tests/e2e/test_order_flow.py
def test_create_order(page):
    page.goto("http://localhost:8000/")
    page.fill("input[name='table_no']", "12")
    page.click("button[type='submit']")
    assert page.locator("#order-list li").count() > 0

C.5.2E2Eテストのデバッグ

テスト実行時に失敗が発生した場合、ターミナルのログ出力をそのまま指示に含めてデバッグを依頼します。

PROMPTE2Eテストが動かない理由をデバッグしてください。@terminal

リダイレクト処理や権限（管理者ロール）の制限が原因で発生するエラーを特定し、修正を適用します。E2Eで落ちる原因の多くは実装の誤りではなく、テスト側が前提条件を用意できていないことです。

C.5.3追加のE2Eテストと機能修正

「メニュー新規登録」「注文登録」「席管理」などの各登録フローに対してE2Eテストを追加し、イテレーティブに修正を進め、全テストのパスを目指します。

E2Eが通るまでは完了としない 6.4.4で「テストが通るのに動かない」という症状に触れました。原因はたいていモックの作り過ぎです。単体テストが全部緑でも、E2Eを1本通すまでは実装が完了したとは言えません。

C.6商用リリースまでに取り組むべきこと

アプリケーションが正常動作した後の「商用運用」に向け、以下の観点について準備・強化を行います。デプロイ先がクラウドでもコンテナでも、項目としては共通です。

  • マルチ環境の整備：本番環境（Production）と検証環境（Staging/Dev）の分離と設定
  • 監視・ログ・アラート体制：メトリクス監視、ログ収集粒度の決定、アラート通知の自動化
  • セキュリティの強化：WAFの導入、シークレット管理の外部化、権限の最小化
  • パフォーマンスとコスト最適化：費用アラート、キャッシュ最適化
  • 運用体制の構築：インシデント対応手順書、定期メンテナンスやパッチ適用の自動化
依存更新は運用の一部です 依存の自動更新（Renovateなど）が効いてくるのはここから先です。エージェントは書いた時点の依存を固定するだけで、その後の更新は誰かがやらなければなりません。PART 4で見た「古い依存」は、作るときだけの問題ではなく、放置すれば必ず起きる問題です。
