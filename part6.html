6.1この章で足すもの

MISSIONPART 5で作ったFlask版 Vibe Chat に、機能を1つ足しなさい。 何を足すかは、この章の途中で届きます。 既存のテストを1つも壊さずに進めなさい。

6.1.1なぜテストがあると違うのか

PART 4では、直したあとにSendが動くかDeleteが動くかを、あなたが手で確かめました。Clineの報告は根拠にならなかったからです。

いまはテストがあります。機能を足したあと、pytest を1回打つだけで、既存の動作が壊れていないか分かります。

これが「テストを盾にする」ということです テストは、正しさを証明するものではありません。前と同じように動くことを確かめるものです。

機能を足すたびに全部を手で確かめるのは無理です。だから、確かめられる部分を先にテストにしておきます。PART 5でやったのは、その準備でした。

6.1.2始める前の確認

pytest を実行して、いま通ることを確認してください。

pytest

落ちている状態で機能を足すと、あとで落ちたのが元からなのか、今回の変更のせいなのか分からなくなります。

6.2実装を進める5つの手順

この章では、次の5手順で機能を足します。先にこれを覚えてください。6.3で、この順に進めます。

1　完了条件を書く　何ができたら終わりか

2　変わる場所を予想する　どのファイルのどこが変わるか

3　Planで依頼する　計画を読んでから実装させる

4　差分を承認する　予想と合っているか確かめる

5　pytest とブラウザで確認する　両方やる

6.2.1手順を飛ばすと何が起きるか

飛ばした手順起きること
1 完了条件Agentが勝手に決める。「完成しました」の意味が分からない
2 予想差分を読んでも、それが妥当か判断できない
3 Plan実装が始まってから方針の誤りに気づく
4 承認関係ない場所まで書き換えられる
5 確認テストは通るが画面が壊れている、が起こる
2番がいちばん飛ばされます 予想を書かずに差分を見ると、読んでいるつもりで読めていません。「それらしいコードだからSave」になります。

先に「app.py のこの関数と、templates/index.html のこの部分が変わるはずだ」と書いておくと、差分が予想と違ったときに気づけます。

6.3予定外の変更要求

動くものが一度できたあとに、要件が変わります。実務ではこちらが普通です。

緊急連絡 投稿の内容に、他人を傷つける言葉が含まれていた、という報告がありました。

禁止語を含む投稿を登録できないようにしてください。禁止語の一覧は app.py の中にリストとして持ちます。

登録を拒否したときは、画面に理由を表示します。既存の機能は1つも壊さないでください。

6.3.1まず、自分で予想する

Agentに投げる前に書いてください。予想を書いてから差分を見るのと、いきなり差分を見るのとでは、レビューの質がまったく違います。

  • データはどう変わるか（禁止語のリストをどこに置くか）
  • 処理はどう変わるか（送信のどの時点で判定するか）
  • 画面はどう変わるか（拒否の理由をどこに出すか）
  • 既存のテストのうち、どれが落ちるか
最後の項目を考えてください 既存のテストは「空の名前は登録されない」「空のメッセージは登録されない」でした。禁止語の判定を足すと、これらは落ちますか。

落ちないはずです。落ちるとしたら、実装が既存の処理を壊しています。

6.3.2完了条件を書く

条件確かめ方
1禁止語を含む投稿は登録されないテスト
2禁止語を含まない投稿は、これまでどおり登録されるテスト
3拒否されたとき、理由が画面に出る人間が見る
4既存のテストが全部通ったままテスト

2番を忘れないでください。「禁止語を弾く」だけを頼むと、全部弾く実装でもテストが通ります。

6.3.3依頼する

PROMPTAdd a banned-word check to the Flask Vibe Chat. Requirements: - Keep a list of banned words in app.py - A message containing a banned word must not be added to the list - Show the reason on the page when a message is rejected - A message without banned words must still be added as before - Add a test for a rejected message - Add a test for an accepted message - Do not change the existing tests Edit app.py, templates/index.html and tests/test_app.py only. Keep the plan under 10 lines. Do not edit the file yet. Show the plan only.

6.3.4差分を見るときに確かめること

確認なぜ
既存の空チェックが残っているか新しい判定に置き換えられていないか
禁止語の判定は、大文字小文字を区別するかどちらでもよいが、意図して決まっているか
拒否の理由は、どこに出るか画面で確認できる形か
既存のテストが書き換えられていないか書き換えられていたら理由を確かめる

6.3.5確認する

pytest

4つのテストが通るはずです。既存の2つと、今回の2つ。

そのあとブラウザで、禁止語を含む投稿と含まない投稿を、それぞれ試してください。

ここでPART 5が効いています 機能を足しましたが、既存の動作が壊れていないことを、コマンド1回で確かめられました。

テストがなければ、送信、削除、空チェック、禁止語。4つを毎回手で確かめることになります。

6.5この章で分かったこと

機能を1つ足しました。既存の動作が壊れていないことは、pytest が教えてくれました。

PART 4では、直すたびにSendとDeleteをあなたが手で確かめました。この章では、それをコマンド1回で済ませました。

テストは正しさを保証しません テストが通っても、仕様が間違っていれば、間違ったとおりに正しく動くだけです。

禁止語のリストに何を入れるか。拒否したとき何を表示するか。それを決めるのは人間です。テストは、決めたことが守られているかを見ているだけです。
